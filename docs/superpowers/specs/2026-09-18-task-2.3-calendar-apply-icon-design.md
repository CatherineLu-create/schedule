# Task 2.3 Calendar Apply and Native Icon Design Amendment

Date: 2026-09-18

Status: Design checkpoint for human review. Calendar Slice 2 remains blocked until its later implementation, real browser verification, independent implementation review, and human acceptance. Task 2.3 remains open.

## Decision and precedence

This amendment supersedes the immediate native-selection save and the separate visible `Calendar` text button in [the 2026-09-17 layout/calendar design](2026-09-17-task-2.3-schedule-layout-calendar-design.md). Chrome 153 emitted a complete provisional date on month navigation and emitted native `change` after focus loss without a day click. Therefore native `input`, `change`, focus, blur, picker dismissal, and month/year navigation are never evidence of an Apply action. The earlier design remains authoritative for the accepted Master → Resources → Schedule layout, `Shown below`, one Schedule, and every lifecycle and Published/Draft rule not changed here. The prior design document remains unchanged.

The user approved **Apply Date plus the native date icon only**. A field's displayed candidate is temporary UI state. Clicking `Apply Date` is the only way to submit a non-null date through the existing `onUpdateMilestone` callback and command/reducer bridge. Clicking `Clear` is the only way to submit `null`. Neither action is Save Draft: accepted updates still replace the one canonical embedded Working Draft in `PrototypeState.schedules` for the exact ProjectId.

## Field state and transitions

Each Draft Plan and Actual retains one enabled, mutable `<input type="date">`, labelled with Project, milestone occurrence, and field. The browser's own visible calendar indicator remains unobscured and operable by pointer and native keyboard. Remove the extra `Calendar` text button and its `showPicker()` handler. Do not make the input readonly, hide the indicator, install a calendar package, or add a custom picker. The input's normalized `value` string is the only date candidate source; use existing `parseDateOnly()` and `DateOnly | null`, never `Date`, locale parsing, or timezone conversion.

Local editor state is keyed by `[projectId, milestoneId, field]` and starts from the canonical `value ?? ""`. Activating the input by focus, pointer, or keyboard reveals a compact field action row. Native events update only its candidate and feedback. If a browser emits no event when the popup opens or closes, the candidate is unchanged. Native popup Escape is a browser dismissal, not the application's `Cancel` action. If the browser restores the old value on Escape, the candidate follows it; if the browser leaves a provisional value, that value remains unapplied and guarded until an explicit field action. No native event calls the canonical update callback.

| Current field condition | User action | Local result | Canonical write / Publish guard |
| --- | --- | --- | --- |
| Inactive, canonical date or legal `null` | Focus, open native icon, navigate month/year, dismiss without a changed value | Show actions while active; hide them on clean exit | None; no guard |
| Active | Native `input` or `change`, including provisional complete, empty, or invalid value | Replace displayed candidate; show `Date not applied` when it differs from canonical or is incomplete | None; guard while unapplied |
| Candidate equals canonical again | Native reversion or field `Cancel` | Restore canonical display; clear local error and action row on Cancel | None; guard clears for that field |
| Valid nonempty candidate differs from canonical | Click `Apply Date` once | Validate the displayed value with `parseDateOnly()` and request one update for this milestone and field | One `DateOnly` callback; guard remains until canonical props reflect the value |
| Empty, invalid, or incomplete candidate | Attempt Apply | Apply is disabled; associated explanation remains visible | None; guard remains while unapplied |
| Any field value | Click `Clear` | Display empty candidate and request canonical `null` | One explicit null callback; guard remains until canonical props reflect `null` |
| Pending Apply or Clear is rejected | Command feedback / unchanged canonical props | Keep the candidate and `Date not applied` feedback; allow deliberate retry or Cancel | No automatic retry; guard remains |

`Apply Date` and the application's `Cancel` are named, focusable buttons associated with their specific labelled input. They appear only for a field being edited or holding an unapplied candidate, including a pending or rejected action; clean inactive rows show neither. `Clear` remains an explicit field action. Several edited fields may retain their own compact action rows so no candidate disappears merely because another field receives focus. An unchanged legal `null` is never invalid or Publish-blocking. A sanitized empty native event during an edit is different from the original null state and must not erase a saved date. For a date already equal to canonical, no Apply is needed.

An accepted Apply or Clear is reflected by canonical props, then local candidate/feedback and action visibility reconcile to that canonical value. The current `unappliedEditors` Publish guard remains active for any uncommitted or command-rejected field. It disables both the main Publish control and an already-open Publish confirmation. `Discard Draft` keeps its existing behavior. Field `Cancel` only abandons that field's candidate; it does not invoke Draft Discard or close an unrelated Publish confirmation. Published snapshots, Current Schedule, and Portfolio remain unchanged until the existing explicit Publish flow succeeds.

Local candidates have no persistence. Leaving the Project for Dashboard, switching Project, changing editor identity or mode, or removing a milestone abandons that editor's pending candidate and clears its guard; returning shows only canonical data. No navigation silently applies. A successful Apply or Clear persists in the mounted app through the existing canonical Working Draft path and survives Dashboard/Project navigation, without cross-Project leakage or refresh/restart storage.

## Compact layout and accessibility

Keep the existing five business columns and the accepted Master → Resources → Schedule order. Place date input and `Clear` within each date cell. When a field is active or unapplied, place compact `Apply Date` / `Cancel` controls and feedback within that cell, allowing wrapping below the input rather than widening every row. Keep the milestone cell's applicability and `Remove` control reachable at the accepted desktop viewport and through the existing horizontal scroll on narrower screens. Do not add a business column or cover `Remove` with an overlay.

The input and each visible field action identify ProjectId, occurrence MilestoneId, and Plan versus Actual in their accessible names or associated context. Associate `Date not applied` with the affected input; `aria-invalid` reflects an incomplete/invalid or unapplied candidate, while a clean legal null is valid. Retain native keyboard date editing and native indicator access. A separate accessible calendar text button is absent; the labelled native input remains the accessible calendar control.

## Acceptance and later gates

- Behavioral tests first prove native `input` and `change` events, month/year provisional values, blur, and dismissal produce **zero** `onUpdateMilestone` and reducer writes. Only one explicit `Apply Date` click can submit a valid candidate once; `Cancel` restores canonical display without a write; `Clear` submits null and reopening the native picker still works.
- Cover initially-null and populated Plan and Actual, including invalid/empty candidates, command rejection, multiple pending fields, already-open Publish confirmation, row removal, identity changes, navigation, exact Project isolation, and Published-only official reads. Replace obsolete exact-label queries in the existing test diff.
- In a real isolated browser/profile at the verified app URL, use the **native icon** to open null and populated Plan and Actual, including after Clear. Change month/year without Apply, dismiss with Escape/outside click, select a day, then use Apply Date, field Cancel, Clear, keyboard editing, and Dashboard/Project navigation. Observe canonical state and Publish/Current Schedule/Portfolio behavior. DOM `input.value` injection, mocked `showPicker`, and an HTTP response do not prove a usable popup. Record browser/platform and any limitations; agent inspection does not replace final human acceptance.
- Later implementation stays in `src/scheduleWorkspace.tsx`, `src/scheduleWorkspace.spec.tsx`, and `src/legacy/characterization/runtime.spec.tsx` unless a concrete extra-scope need is brought to the human. Preserve layout Slice 1 and all existing domain, command, selector, catalog, N/A, A/A2, confirmation, and lifecycle decisions. No dependency, parser, backend, storage, custom calendar, or business-rule change.
- The premature canonical update is an open **Important** finding; the obsolete-label test is an open **Minor** finding. Both remain open until implementation review. Clear/reopen requires real browser verification. After focused/adjacent tests, full suite, build, static/diff checks, real browser verification, and fresh independent implementation review pass, stop for human UI acceptance. This document authorizes no implementation or closure.
