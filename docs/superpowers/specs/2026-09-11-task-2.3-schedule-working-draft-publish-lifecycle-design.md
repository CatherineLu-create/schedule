# Task 2.3 — Schedule Working Draft + Publish Lifecycle Design

**Status:** Approved human design decisions; documentation only; implementation is not authorized by this document

## 1. Context

Task 2.1 made `PrototypeState.projects` the sole Project/Master authority.
Task 2.2 then separated Schedule ownership from Project and established:

- `PrototypeState.schedules` as the sole canonical Schedule authority;
- exactly one `CanonicalProjectSchedule` per immutable `ProjectId`;
- no `ScheduleId`, Published `VersionId`, or mutable Current pointer;
- immutable Published snapshots identified by `(ProjectId, versionNumber)`;
- Current Published derived by maximum `versionNumber`;
- official Schedule reads that distinguish unavailable, no Published Schedule,
  and Published;
- a Current-only, read-only Workspace Schedule;
- legacy Schedule write types and commands physically present but disconnected
  from canonical state and runtime.

The current canonical Schedule model contains `projectId` and
`publishedVersions`. Task 2.3 extends that same aggregate with one optional
Working Draft and adds the canonical lifecycle from Official Truth to a new
immutable Published version. It does not restore any predecessor Draft,
Version ID, row ID, import, or version-history model.

The governing lifecycle is:

```text
Official Truth
    → Working Draft
    → PM edits
    → Discard Working Draft
      OR
    → Publish confirmation
    → new immutable Official Truth
```

This specification is a design checkpoint only. It does not authorize source
or test changes, an implementation plan, implementation work, or Task 2.4.

## 2. Goals

Task 2.3 must:

1. add zero-or-one canonical Working Draft directly to each canonical
   Schedule;
2. initialize a Draft from Current Published or an empty Schedule without
   changing Published truth;
3. support immutable Draft transitions for milestone add, update, and remove;
4. persist each valid Draft edit immediately in `PrototypeState.schedules`;
5. allow the entire Draft to be discarded, including when it is malformed;
6. publish a valid Draft atomically as the next immutable Published snapshot;
7. keep official reads isolated from all Draft content and Draft defects;
8. provide a distinct canonical Draft read boundary and Workspace Draft mode;
9. preserve exact ProjectId ownership, milestone lineage, Task 2.1 behavior,
   Task 2.2 official-read behavior, Portfolio isolation, Team gating, and
   legacy isolation.

## 3. Non-Goals

Task 2.3 does not add:

- PPT Import;
- Evidence, Candidate, Proposal, or Review workflow;
- Rollback;
- Published history selection, comparison, or version switching;
- version-note input;
- a Draft base-version field;
- multi-user conflict detection or optimistic concurrency;
- Draft owner, editor, timestamps, audit history, or autosave history;
- custom free-text milestone definitions;
- Portfolio Current Stage, MDRR, Milestone Due, warning, or Needs Attention
  derivation;
- Team migration;
- authentication, backend, database, or persistence architecture;
- Provider, Context store, repository, or service abstractions.

## 4. Existing Task 2.2 Boundary

The following committed boundaries remain authoritative:

- Canonical `Project` contains `id`, `master`, `identityAliases`, and `team`.
  It does not contain Schedule state.
- `PrototypeState` has one `projects` collection and one `schedules`
  collection.
- Schedule ownership is exact `ProjectId`; Project names are never identity.
- `CanonicalPublishedScheduleVersion` and
  `CanonicalPublishedScheduleMilestone` are readonly official snapshots.
- `validateCanonicalProjectSchedule()` validates Published integrity only.
- `getCurrentPublishedVersion()` selects the maximum version number.
- `selectCurrentPublishedSchedule()` exposes only Current Published and never
  exposes Published history or the owning Schedule.
- `OfficialScheduleView` presents unavailable, no-Published, and Published
  official-read states.
- Project creation atomically adds one Project plus one same-ID empty
  canonical Schedule.
- Project Master remains the Workspace landing resource and Team remains
  disabled as `Migration pending`.

Task 2.3 extends these contracts. It does not replace them with a second state
model or route canonical behavior through predecessor `ProjectSchedule`,
`ScheduleWorkingDraft`, `startProjectScheduleWorkingDraft()`, or
`publishProjectSchedule()`.

The canonical model may continue using the current shared
`MilestoneApplicability` and `ScheduleVersionNumber` value types. This does not
authorize use of predecessor Draft, Version ID, row ID, or write-command
types.

## 5. Canonical Data Model

The canonical Schedule shape becomes conceptually exact as follows:

```ts
export interface CanonicalScheduleWorkingDraftMilestone {
  readonly milestoneId: MilestoneId;
  readonly milestoneDefinitionId: MilestoneDefinitionId;
  readonly applicability: MilestoneApplicability;
  readonly plan: DateOnly | null;
  readonly actual: DateOnly | null;
}

export interface CanonicalScheduleWorkingDraft {
  readonly milestones: readonly CanonicalScheduleWorkingDraftMilestone[];
}

export interface CanonicalProjectSchedule {
  readonly projectId: ProjectId;
  readonly publishedVersions: readonly CanonicalPublishedScheduleVersion[];
  readonly workingDraft: CanonicalScheduleWorkingDraft | null;
}
```

`workingDraft` is required and explicitly holds either a Draft or `null`.
Missing or `undefined` Draft properties are not alternative canonical
representations.

The Working Draft intentionally has no:

- `DraftId` or `ScheduleDraftId`;
- `baseVersionNumber` or base Published identity;
- created/updated timestamp;
- owner or editor;
- review status;
- version note;
- import, evidence, proposal, or review metadata.

Although the Draft is editable business state, its TypeScript structures are
readonly. Editing occurs by pure replacement transitions, not in-place
mutation.

`createEmptyCanonicalProjectSchedule(projectId)` must return exactly the
same owner, an empty Published history, and `workingDraft: null`.
Canonical Schedule fixtures must add the explicit `workingDraft: null` state;
Task 2.3 does not fabricate initial Drafts for fixture Projects.

## 6. Authority and Identity

The authority tree remains:

```text
PrototypeState
├─ projects[]   — sole Project/Master authority
└─ schedules[]  — sole Schedule, Published, and Working Draft authority
```

The one-to-one Project/Schedule invariant remains unchanged. A Schedule owns
zero or one Working Draft; there is no `PrototypeState.scheduleDrafts`, Draft
map, component-owned Draft business object, cache, or second Draft authority.

Identity rules are:

- Schedule owner: `ProjectId`;
- Published snapshot: `(ProjectId, versionNumber)`;
- business milestone: `(ProjectId, milestoneId)`;
- occurrence in a Published snapshot: `(ProjectId, versionNumber,
  milestoneId)`.

The same `milestoneId` across Published versions of one Project represents
lineage. The same raw milestone ID may occur in another Project because
ProjectId scopes business identity. `milestoneDefinitionId` is classification,
not identity. A display name is never identity.

No canonical Task 2.3 model or action may introduce `ScheduleId`, `VersionId`,
`ScheduleVersionId`, `DraftId`, `ScheduleDraftId`, `MilestoneRowId`, or
`currentPublishedVersionId`.

## 7. Working Draft Initialization

`startScheduleWorkingDraft()` is a new canonical pure lifecycle command.
Its semantic input is the current `CanonicalProjectSchedule` plus the
canonical milestone-definition context needed for validation. It returns a
discriminated result and never dispatches or mutates state.

The command follows this order:

1. If `workingDraft` already exists, return an `existing` success with the
   exact existing Draft and unchanged Schedule. Do not rebuild, validate away,
   or overwrite the Draft, including a malformed existing Draft.
2. If no Draft exists, validate Published integrity through the Task 2.2
   Published validation boundary. Invalid Published history returns
   `validation-failed` with issues and no mutation.
3. Derive Current Published through `getCurrentPublishedVersion()`.
4. If Current Published exists, create a Draft with a new milestone array and
   new milestone objects whose values and `milestoneId` values are copied from
   that snapshot.
5. If no Published version exists, create an empty Draft.
6. Return a `created` success containing a new Schedule with the Draft.

Start Draft is idempotent:

- first action with no Draft: `created`;
- later action while that Draft exists: `existing`;
- existing edits are preserved exactly;
- no additional identity is allocated.

Copying Published to Draft never aliases the Published milestone array or its
milestone objects. Published values remain unchanged.

## 8. Draft Milestone Editing

Canonical Draft editing consists only of add, update, and remove transitions.
Every successful transition returns a new `CanonicalProjectSchedule` with the
same `projectId` and unchanged Published history.

### 8.1 Update existing milestone

`updateScheduleWorkingDraftMilestone()` identifies the Draft milestone by
`milestoneId`. Its public input can change only:

- `applicability`;
- `plan`;
- `actual`.

It has no `milestoneDefinitionId` field or generic arbitrary-property patch.
Changing the definition means removing the old business milestone and adding
a new milestone with a new ID.

The command preserves `milestoneId` and `milestoneDefinitionId`. A missing
Draft returns `no-working-draft`; a missing milestone returns
`milestone-not-found`. A structurally malformed Draft returns
`validation-failed` and is not partially repaired by ordinary editing.

Changing applicability to `notApplicable` does not erase Plan or Actual.
There is no approved destructive normalization rule.

### 8.2 Add milestone

`addScheduleWorkingDraftMilestone()` receives:

- a newly allocated `MilestoneId`;
- a `milestoneDefinitionId` selected from the canonical
  `milestoneDefinitions` catalog.

Identity allocation occurs at the application/UI boundary once per Add
attempt and is passed into the pure command. No ID service is introduced and
the domain command does not call `crypto.randomUUID()`.

The command rejects an unresolved definition and a duplicate `milestoneId`
with `validation-failed` plus precise Draft validation issues. On success it
appends a milestone with:

```text
applicability = applicable
plan = null
actual = null
```

Two Draft milestones may share `milestoneDefinitionId` when their
`milestoneId` values differ. The add UI must not disable a definition merely
because another row already uses it. A removed milestone that is later
recreated, even with the same definition or display name, receives a new
`milestoneId`.

### 8.3 Remove milestone

`removeScheduleWorkingDraftMilestone()` removes exactly one Draft milestone by
`milestoneId`. It does not alter Published snapshots. No Draft returns
`no-working-draft`; an absent ID returns `milestone-not-found`.

Ordinary add, update, and remove commands do not operate on a malformed Draft.
The recovery action for malformed Draft data is the separately defined
discard command.

## 9. Validation and Integrity Boundaries

Published and Draft validation remain separate.

`validateCanonicalProjectSchedule()` continues to validate only
`publishedVersions` with the Task 2.2 rules. Adding `workingDraft` to the
Schedule object must not cause this function or
`selectCurrentPublishedSchedule()` to consume Draft content or Draft errors.

A new pure boundary, conceptually
`validateScheduleWorkingDraft(draft, milestoneDefinitions)`, performs only:

- duplicate `milestoneId` detection within the Draft;
- unresolved `milestoneDefinitionId` detection.

The Draft validator returns blocking `ValidationIssue` entries with these
exact codes so callers can distinguish Draft defects from Published defects:

- `schedule.draft.integrity.duplicate-milestone-id`;
- `schedule.draft.integrity.unresolved-milestone-definition`.

Draft validation does not require:

- Plan or Actual;
- Plan before Actual;
- any mandatory milestone or Stage completeness;
- unique `milestoneDefinitionId`;
- clearing dates for `notApplicable`;
- a base Published version;
- active or reviewed catalog metadata;
- date chronology or due-state policy.

An empty Draft is valid and publishable.

`validateCanonicalScheduleState()` remains the whole-state diagnostic
boundary. It continues to report all Project/Schedule ownership and Published
issues, and additionally reports Draft issues for each non-null Draft. This
global diagnostic expansion must not be reused to gate an otherwise healthy
selected official read: official selection remains selected-Schedule and
Published-only.

## 10. Command and Result Contracts

Task 2.3 introduces new canonical commands:

- `startScheduleWorkingDraft`;
- `updateScheduleWorkingDraftMilestone`;
- `addScheduleWorkingDraftMilestone`;
- `removeScheduleWorkingDraftMilestone`;
- `cancelScheduleWorkingDraft`;
- `publishScheduleWorkingDraft`.

Each command is a pure transition:

```text
current CanonicalProjectSchedule + explicit command input
    → success(next CanonicalProjectSchedule, operation data)
      OR
    → explicit failure(reason, ValidationIssue[] when applicable)
```

Success results always carry the complete replacement Schedule. Start Draft
also carries `created | existing` and the selected Draft. Publish also carries
the new Published version. Failures never return a candidate for dispatch.

The lifecycle failure reasons are deliberately separate:

- `no-working-draft`;
- `milestone-not-found`;
- `validation-failed`;
- `next-version-unavailable`.

Project/Schedule ownership failures remain application-boundary integrity
issues such as `project-not-found`, `missing-schedule`, and
`duplicate-schedule`; they are not collapsed into a lifecycle reason.
Validation details remain in `ValidationIssue[]`. A single vague Schedule
error is not an acceptable replacement for these distinctions.

The commands do not:

- mutate input objects or arrays;
- dispatch reducer actions;
- read or mutate React state;
- access Project name identity;
- directly mutate `PrototypeState`;
- call predecessor Schedule commands.

Immediate edit commands return `validation-failed` if the current Draft is
already malformed. `cancelScheduleWorkingDraft()` is the sole lifecycle
command allowed to clear a malformed Draft without first validating it.

## 11. Canonical Ownership Resolution

Lifecycle controllers require the complete canonical Schedule as a command
input, while Workspace views require presentation-only read results. These
concerns must not be combined by exposing a writable Schedule through the
official presentation result.

The application selector layer therefore owns one reusable exact-owner
resolution rule, conceptually:

```text
resolve canonical Schedule owner(state, projectId)
    → available(exact CanonicalProjectSchedule)
      OR
    → unavailable(ownership ValidationIssue[])
```

It checks exact Project existence and exactly one matching Schedule. It does
not validate Published or Draft business content. Official selector, Draft
selector, and lifecycle controller reuse this ownership rule. No caller may
choose the first duplicate, manufacture a missing Schedule, or resolve by
Project name.

This is a thin selector/application boundary consistent with Task 2.2, not a
repository or service abstraction.

## 12. Atomic State Transitions

The canonical reducer gains one Schedule replacement action conceptually
equivalent to:

```ts
{
  readonly type: "scheduleReplaced";
  readonly projectId: ProjectId;
  readonly schedule: CanonicalProjectSchedule;
}
```

The reducer enforces authority invariants only:

- action `projectId` equals `schedule.projectId`;
- the Project exists;
- exactly one current Schedule has that ProjectId;
- only that one Schedule is replaced;
- `state.projects` is preserved by reference.

It does not reimplement Draft initialization, milestone editing, validation,
or next-version calculation. A failed invariant check leaves both root
collections unchanged.

The application flow is:

```text
UI intent
    → exact canonical Schedule owner resolution
    → canonical lifecycle command
    → optional disposition interpretation
    → one scheduleReplaced reducer action on success
    → PrototypeState.schedules
```

Failures dispatch nothing. The UI never mutates a Schedule directly.

Project creation retains the existing atomic `projectAdded` action. Its empty
Schedule must now have both `publishedVersions: []` and `workingDraft: null`;
the reducer rejects a creation Schedule with Published history or a non-null
Draft. Rejected Create and duplicate review-required Create still create
neither Project nor Schedule. Create Anyway still reuses the original
ProjectId and creates exactly one same-ID empty Schedule after completion.

## 13. Publish Semantics

`publishScheduleWorkingDraft()` always creates a new immutable Published
snapshot and never mutates or replaces an old version.

Its input includes the current canonical Schedule, canonical definition
context, and one externally supplied `publishedAt` string. It does not accept
`versionNumber` or `versionNote` from the caller.

At execution the command performs this order:

1. Require a Working Draft; otherwise return `no-working-draft`.
2. Revalidate the existing Published history with the Task 2.2 Published
   validation boundary.
3. Revalidate the Working Draft with the Draft validation boundary.
4. If either validation has blocking issues, return `validation-failed` with
   all applicable issues and no mutation.
5. Find the maximum existing Published `versionNumber`.
6. If no Published version exists, select version 1.
7. Otherwise select maximum plus one. For `[v1, v3]`, the result is v4,
   independent of array order.
8. If maximum is `Number.MAX_SAFE_INTEGER`, return
   `next-version-unavailable`; do not construct an unsafe version.
9. Create a new Published version with the supplied `publishedAt`,
   `versionNote: null`, and copied Draft milestone values and IDs.
10. Return one replacement Schedule that appends the new version and sets
    `workingDraft: null`.

One shared pure calculation, conceptually
`getNextPublishedScheduleVersionNumber(schedule)`, returns the next safe
version or an unavailable result. The Publish command calls it at execution.
A UI preview such as `Publish as v04` may call the same calculation, but the
preview is not command input or identity authority.

The application/UI controller captures one timestamp at the user's Publish
confirmation and supplies it to the pure command. Domain logic, commands, and
the reducer do not call `new Date()`. No Clock service is introduced.

The new Published milestone array and each milestone object are distinct from
the Draft array and objects. They preserve value fields and `milestoneId`
lineage. Appending creates a new outer `publishedVersions` array without
mutating the previous history array; every pre-existing Published version,
its milestone array, and its milestone objects retain their references and
values.

An empty valid Draft publishes successfully as a zero-milestone snapshot.
Publish failure preserves the Draft and every Published snapshot exactly.

Double Publish is deterministic: the first success appends one version and
clears the Draft; a second command against the resulting Schedule returns
`no-working-draft` and cannot append another version.

## 14. Cancel Semantics

`cancelScheduleWorkingDraft()` means discard the complete Working Draft.

On success it returns a new Schedule with:

```text
workingDraft = null
publishedVersions = the unchanged Published history
```

It performs no Draft validation, so a malformed Draft can always be
discarded. If no Draft exists, it returns explicit `no-working-draft` failure
rather than silent success.

There is no Draft history, undo, recovery, or per-edit rollback. Double Cancel
therefore produces one success followed by `no-working-draft`.

## 15. Selector and Read Boundaries

### 15.1 Official read

`selectCurrentPublishedSchedule(state, projectId)` retains Task 2.2 semantics.
It reads ownership and Published business content only. It ignores
`workingDraft`, including a malformed Draft.

Examples:

```text
healthy Published v03 + edited valid Draft
    → Published v03

healthy Published v03 + malformed Draft
    → Published v03
```

A bad Draft never turns healthy official truth into `unavailable`. Working
Draft content never enters official milestone rows, Dashboard, or Export.

### 15.2 Draft read

A new canonical boundary, conceptually
`selectScheduleWorkingDraft(state, projectId)`, distinguishes:

- `unavailable`;
- `noWorkingDraft`;
- `workingDraft`.

It uses the exact-owner resolution rule. With one Schedule owner:

- `workingDraft: null` returns `noWorkingDraft`;
- a valid Draft returns `workingDraft` with the exact readonly Draft and
  projected editor rows;
- a malformed Draft returns `unavailable` with its Draft issues and an
  explicit `workingDraftExists: true` capability indicator.

Ownership failure returns `unavailable` with `workingDraftExists: false`.
This distinction lets the Workspace display Draft corruption and offer
Discard without exposing malformed rows as editable presentation data.

Draft rows contain:

- `milestoneId`;
- Phase display `"-"`;
- Stage display resolved from the definition's `stageGroupId` and
  `stageGroupCatalog`;
- Milestone display resolved from `milestoneDefinitions`;
- `applicability`;
- `plan: DateOnly | null`;
- `actual: DateOnly | null`.

Plan and Actual remain typed values for editing. The Draft selector does not
format them into display strings and later parse them back. It orders rows by
the same milestone-definition `displayOrder` rule as Published presentation;
equal orders preserve Draft snapshot relative order. It does not sort by name,
date, status, or ID.

Draft selection validates Draft content only after ownership succeeds.
Published defects remain separately visible through whole-state diagnostics,
the official read, and Publish revalidation. An unrelated Project's defects
never suppress the selected Draft.

## 16. Workspace UI State Machine

Schedule Workspace has exactly two business modes:

```text
Official Read Mode
    Edit success → Working Draft Mode

Working Draft Mode
    Publish success → Official Read Mode
    Discard success → Official Read Mode
```

There is no Review Mode and no Resume Draft action.

The mode is derived from selected `ProjectId` and the canonical Draft read on
every render; it is not stored as a second business-state flag:

- `noWorkingDraft` means Official Read Mode;
- a valid `workingDraft` means Working Draft Mode;
- `unavailable` with `workingDraftExists: true` means Working Draft Mode in
  its invalid-data presentation;
- ownership unavailable retains the official Schedule unavailable state and
  cannot start editing.

Leaving Workspace or returning to Dashboard does not dispatch Cancel. When
the same Project is reopened, an existing Draft enters Working Draft Mode
directly. Selecting another Project derives only that Project's Draft; no
Draft object or mode leaks across Projects.

Project Master remains the default Workspace resource for Dashboard open,
Create completion, and Review Existing. Schedule navigation does not change
`selectedProjectId`. Project Master remains usable when Official or Draft
Schedule data is unavailable. Team remains disabled and is not a
`WorkspaceResource`.

## 17. Official Read Mode

Official Read Mode preserves Task 2.2 unavailable, no-Published, Published,
and Published-zero-milestone presentation. It displays Current Published only
and adds one `Edit` action.

The Edit action is available only when exact ownership is resolved and the
canonical start command can be attempted. On command success, the single
Schedule replacement causes the derived mode to become Working Draft. On
failure, no state is dispatched and precise feedback remains local to the
Schedule resource.

Official mode does not display:

- Add Milestone or Remove controls;
- editable fields;
- Publish or Discard Draft;
- Working Draft content;
- Published history or a history selector.

## 18. Working Draft Editing UX

Working Draft Mode is headed exactly with `Working Draft`. It must not claim
`Based on Published vXX`, because the canonical Draft has no base-version
metadata and such provenance cannot be reconstructed reliably.

The table retains exactly five business columns:

1. Phase
2. Stage
3. Milestone
4. Plan
5. Actual

Phase is `"-"` and read-only. Stage and Milestone are catalog-derived and
read-only for existing rows. Applicability is displayed and edited beside the
Milestone name as `Applicable` or `Not applicable`; it is not a sixth business
column. A row Remove action may also appear beside the Milestone content and
does not create a new business-data column.

Plan and Actual editors represent `DateOnly | null`. Clearing an editor
dispatches `null`. A complete value is parsed with the existing DateOnly
boundary before a command is issued. Invalid or incomplete text remains only
in a transient component input buffer and never enters the canonical Draft.
That buffer is scoped by selected ProjectId, milestoneId, and field, and is
reset or resynchronized when those identities or the canonical value change.
No datetime, timezone, or free-text canonical date is introduced.

Applicability changes and valid Plan/Actual changes execute their canonical
command immediately. Add and Remove do the same. There is no Save Draft
button or parallel unsaved Draft object: the canonical Working Draft is the
saved Working Copy.

Add Milestone presents the existing canonical milestone-definition catalog.
It allocates one new `MilestoneId` when the user confirms an Add attempt and
passes the ID and definition to the command. Definitions already used by
other rows remain selectable. No free-text custom definition is accepted.

Remove needs no per-row confirmation. Discarding the whole Draft uses the
confirmation described below.

## 19. Confirmation UX

Publish uses a lightweight official-truth confirmation, not a Review
workflow:

```text
Publish Working Draft?

This will create a new official Schedule version.
Published versions cannot be edited.

[Keep Editing] [Publish]
```

It may show `Publish as v04` using the shared preview calculation. The command
still recomputes the next version when Publish is confirmed. No version-note
field appears.

Discard uses:

```text
Discard Working Draft?

All unpublished Schedule changes will be discarded.
Published Schedule versions will not be affected.

[Keep Editing] [Discard Draft]
```

Keeping Editing changes no canonical state. Confirming Publish obtains one
timestamp and invokes Publish. Confirming Discard invokes Cancel. Neither
confirmation adds a third business mode.

## 20. Invalid Draft Recovery

If exact ownership resolves but a non-null Draft fails Draft validation, the
Workspace remains visibly in Working Draft Mode and displays:

```text
Working Draft data unavailable
```

It does not:

- convert the Draft to empty;
- treat it as `noWorkingDraft`;
- silently fall back to Official Read Mode;
- render malformed rows as editable;
- allow Publish, Add, Update, or Remove.

Discard Draft remains enabled because Cancel only replaces the Draft with
`null` and leaves Published history intact. After successful discard, the
derived state returns to Official Read Mode. The Project Master resource
remains usable throughout.

The official selector continues to show healthy Published truth independently
of the Draft error. Whole-state diagnostics may report the Draft issues but do
not convert them into Dashboard Needs Attention.

## 21. Error Handling

Errors remain layered:

- ownership/integrity issues describe absent Project, missing Schedule,
  duplicate Schedule, orphan Schedule, Published defects, and Draft defects;
- lifecycle failures describe an operation that cannot be completed;
- transient editor errors describe invalid or incomplete input that has not
  entered canonical state.

The UI displays precise operation or validation feedback inside the Schedule
resource. It does not dispatch on failure, choose an arbitrary owner, create a
missing Schedule during read, normalize malformed data, or fall back to
legacy state.

Workflow interpretation may map canonical command results to completed,
blocked, or rejected presentation dispositions when that improves controller
consistency. It must preserve the original discriminant and issues and must
not accept an invalid candidate. Publish and Discard confirmations are not a
Proposal or Review workflow.

## 22. Legacy, Portfolio, and Team Isolation

Canonical Task 2.3 production code must not import or invoke predecessor:

- `ProjectSchedule` or `ScheduleWorkingDraft` as canonical business state;
- `startProjectScheduleWorkingDraft()`;
- `replaceProjectScheduleWorkingDraft()`;
- `discardProjectScheduleWorkingDraft()`;
- `publishProjectSchedule()`;
- predecessor Draft, Version ID, row ID, import, or stale-base workflow
  interpretation.

Those files and tests may remain physically present and behaviorally
unchanged. They remain unreachable from `PrototypeState`, canonical fixtures,
canonical selectors, canonical Workspace, and the new lifecycle commands.

Portfolio remains isolated:

- Current Stage stays `"-"`;
- MDRR stays `"-"`;
- Needs Attention stays `No items requiring attention.`;
- Milestone Due remains inactive;
- Dashboard and Export continue to use Task 2.1 canonical Project rows and do
  not read the Working Draft.

Team remains disabled with `Migration pending`; no Team domain, command, or UI
migration is part of Task 2.3.

## 23. Test Strategy and Verification Matrix

Future implementation must use behavior-first TDD with compiling skeletons.
RED evidence must be a failure of the intended behavior, not an unresolved
module, malformed fixture, or unrelated TypeScript cascade. Each boundary
must have focused tests, adjacent regressions, the full suite, a production
build, static authority scans, exact scope review, and independent review
before any implementation checkpoint.

### 23.1 Model and authority

Tests must prove:

- `workingDraft` is exactly `null | CanonicalScheduleWorkingDraft` and is not
  optional;
- empty canonical Schedule creation yields `workingDraft: null`;
- every fixture has the explicit Draft property;
- one Schedule per Project remains unchanged;
- no Draft collection or Draft ID exists;
- Project still has no Schedule member;
- Published and Draft arrays are readonly transition inputs;
- `projectAdded` accepts only an empty same-ID Schedule with null Draft.

### 23.2 Start Draft

Tests must prove:

- Current Published is copied by maximum version number, not final array
  position;
- copied milestones retain `milestoneId` and values but do not alias Published
  arrays or objects;
- no Published history creates an empty Draft;
- an existing Draft returns `existing`, preserves its exact object and edits,
  and does not create another Draft;
- malformed Published history blocks creation without mutation;
- repeated Start produces `created` then `existing`.

### 23.3 Immutability and isolation

Tests must prove:

- Draft edits do not change any Published version or milestone;
- old Published snapshots remain unchanged across Publish;
- new Published arrays and milestone objects do not alias Draft data;
- official selector output is identical with no Draft, valid edited Draft, or
  malformed Draft when Published data is healthy;
- failed commands preserve all input references and values.

### 23.4 Milestone identity and update

Tests must prove:

- copied milestone identity is retained;
- applicability, Plan, and Actual update independently;
- definition and milestone identity remain unchanged by update;
- no public update input can mutate `milestoneDefinitionId`;
- switching to not applicable preserves dates;
- a missing Draft and missing milestone produce their distinct failures;
- cross-Project milestone IDs remain Project-scoped.

### 23.5 Add and remove

Tests must prove:

- Add accepts a catalog definition and an externally allocated new ID;
- defaults are applicable/null/null;
- unresolved definition and duplicate milestone ID are rejected;
- duplicate milestone definition is allowed for distinct milestone IDs;
- remove changes Draft only and leaves Published unchanged;
- missing milestone returns explicit failure;
- remove then re-add uses a new milestone ID;
- ordering uses definition display order and preserves relative snapshot order
  for equal display order.

### 23.6 Draft validation and selector

Tests must prove:

- empty Draft is valid;
- duplicate milestone ID and unresolved definition are invalid;
- no issue is invented for null dates, chronology, applicability, missing
  milestones, duplicate definitions, or catalog active/review metadata;
- whole-state diagnostics report Draft defects;
- official selector ignores valid and malformed Drafts;
- Draft selector distinguishes `unavailable`, `noWorkingDraft`, and
  `workingDraft`;
- malformed Draft returns unavailable with `workingDraftExists: true`;
- ownership unavailable returns `workingDraftExists: false`;
- Draft row projection uses catalog Stage/Milestone values, Phase `"-"`,
  canonical order, and raw `DateOnly | null` values;
- unrelated Project defects do not suppress the selected Draft.

### 23.7 Cancel

Tests must prove:

- Draft becomes null;
- Published history remains the same reference and values;
- no Draft returns `no-working-draft`;
- malformed Draft can be discarded;
- two Cancels yield success then no-working-draft;
- reducer applies a successful result in one Schedule replacement.

### 23.8 Publish

Tests must prove:

- no Published history creates v1;
- out-of-order `[v3, v1]` creates v4;
- non-contiguous history uses maximum plus one;
- an empty Draft publishes a zero-milestone snapshot;
- `versionNote` is always null;
- exact supplied `publishedAt` is retained and no domain clock is called;
- old Published history remains ordered, preserved, and unmodified;
- Draft milestone IDs carry into the new Published snapshot;
- the new snapshot does not alias Draft arrays or milestone objects;
- successful append and Draft clear occur in one replacement;
- invalid Draft and invalid Published history return validation-failed with no
  mutation;
- maximum safe version returns next-version-unavailable with Draft intact;
- caller cannot supply version number authority;
- two Publishes yield one success then no-working-draft and no extra version.

### 23.9 Reducer and application integration

Tests must prove:

- `scheduleReplaced` requires matching action and Schedule ProjectIds;
- selected Project exists and exactly one Schedule owner is replaced;
- missing or duplicate owner rejects without partial mutation;
- Project collection and Project identity are unchanged;
- reducer does not calculate Draft content or version numbers;
- every state-changing Start, Add, Update, Remove, Cancel, and Publish
  controller success dispatches one complete command result;
- an `existing` Start result preserves the exact Schedule and Draft and does
  not require a no-op reducer dispatch;
- command failure dispatches nothing;
- ordinary Create and Create Anyway still create exactly one same-ID Schedule
  with null Draft, while rejected/review-required Create creates none.

### 23.10 Workspace and editing UI

Tests must prove:

- Project Master remains the landing resource;
- Schedule with no Draft shows Official Read Mode;
- Edit starts a Draft and enters Working Draft Mode;
- an existing Draft re-enters Working Draft Mode without Resume;
- Publish returns to Official Read Mode with the new Current version;
- Cancel returns to the prior Published or no-Published official state;
- malformed Draft shows Working Draft data unavailable, blocks Publish, allows
  Discard, and leaves Project Master usable;
- the Draft table has exactly Phase, Stage, Milestone, Plan, and Actual;
- existing classification and Phase are read-only;
- Plan and Actual edit, clear to null, and reject incomplete text from
  canonical state;
- applicability edits beside Milestone without a sixth business column and
  does not clear dates;
- Add and Remove are available only in Working Draft Mode;
- no Save Draft exists and every valid business edit updates canonical state;
- publish and discard confirmations preserve state on Keep Editing;
- no Based-on-version label, history selector, Review mode, or Schedule write
  control appears in Official mode.

### 23.11 Navigation and cross-Project isolation

Tests must prove:

- Draft survives leaving and reopening Workspace;
- selecting P002 never displays or edits P001 Draft;
- returning to P001 derives its same Draft by exact ProjectId;
- Project rename does not re-key or lose the Draft;
- unresolved selected Project cleanup never renders stale Draft data.

### 23.12 Portfolio, Team, and legacy regressions

Tests and static scans must prove:

- Current Stage and MDRR remain `"-"`;
- Needs Attention remains canonical-safe empty;
- Milestone Due remains inactive;
- Export remains Task 2.1 all-Project behavior;
- Team remains disabled with Migration pending;
- canonical state, commands, selectors, and runtime do not import or invoke
  predecessor write APIs, predecessor Draft types, legacy Schedule JSON, or a
  live adapter.

## 24. Explicit Forbidden Scope

Task 2.3 must not introduce:

- a second Schedule or Draft authority;
- embedded `Project.schedule`;
- Schedule, Version, Draft, or row IDs beyond the approved ProjectId,
  versionNumber, and milestoneId identities;
- a mutable Current Published pointer;
- direct Published mutation or version replacement;
- caller-supplied Publish version number;
- domain/reducer clock access;
- Draft base version, provenance label, owner, timestamps, or version-note UI;
- free-text milestone definitions or definition mutation;
- Save Draft, autosave history, Undo, or rollback;
- Published history browser, version selector, or comparison;
- Import, Evidence, Candidate, Proposal, or Review behavior;
- Portfolio Schedule derivation or Draft warnings;
- Team migration;
- predecessor Schedule write API reconnection;
- Provider, Context store, repository, service, backend, persistence, login,
  or router architecture.

## 25. Migration and Compatibility Notes

Task 2.3 is an additive evolution of the canonical Task 2.2 Schedule shape.
All existing canonical fixtures and Schedule construction sites must adopt the
required `workingDraft` property. Existing Published values, version numbers,
milestone IDs, ordering, and official read output remain unchanged.

The existing official selector must be regression-protected before and after
Draft lifecycle changes. The whole-state validator gains Draft diagnostics,
but its broader output is never used as a shortcut for selected official-read
availability.

The existing `projectAdded` creation transition must reject a non-null Draft
for a newly created Project. Project replacement behavior remains Project-only
and preserves the Schedule collection. The new `scheduleReplaced` transition
is the sole canonical Schedule write boundary for lifecycle results.

Predecessor Schedule domain and command files may still compile and retain
their own Draft ID, Version ID, row ID, stale-base, import, and validation
semantics. Their physical presence is not canonical compatibility. They must
remain disconnected from the Task 2.3 production path.

## 26. Completion Criteria

Task 2.3 is complete only when all of the following are true:

1. `CanonicalProjectSchedule` requires exactly one nullable Working Draft
   field and canonical empty Schedules initialize it to null.
2. Canonical pure commands implement idempotent Start, immediate immutable
   add/update/remove, explicit Cancel, and atomic Publish.
3. Published validation and official selection remain isolated from Draft
   content and errors.
4. Draft validation and the discriminated Draft selector preserve malformed,
   absent, and valid Draft distinctions without normalization.
5. Reducer application replaces exactly one same-ID Schedule atomically and
   does not duplicate lifecycle rules.
6. Publish computes maximum plus one, handles overflow, injects time, uses a
   null version note, copies snapshot objects, appends once, and clears Draft
   once.
7. Workspace derives exactly Official Read or Working Draft mode from
   canonical state, persists Draft across navigation, and isolates Projects by
   ID.
8. Editing exposes only the approved five-column surface, allowed fields,
   Add/Remove, Publish confirmation, and Discard confirmation, with no Save
   Draft or history/review surface.
9. Malformed Draft recovery permits Discard while keeping official Published
   truth and Project Master usable.
10. Task 2.1 and Task 2.2 behavior, Portfolio isolation, Team gating, and
    predecessor isolation remain green.
11. Focused lifecycle, selector, reducer, UI, runtime, regression, full-suite,
    production-build, static-scan, and authority-audit verification passes.
12. Each future implementation slice is independently reviewed before its
    checkpoint; final whole-task review is clean before Task 2.3 is declared
    closed.

This design does not authorize implementation. A separate human-approved
implementation plan is required before any Task 2.3 source or test change.
