## 1. Context / why Human Acceptance failed

The five Task 2.3 implementation slices passed technical verification. Human
acceptance subsequently failed: a date entered in Manta's Working Draft appeared
to disappear after navigating to Dashboard and returning without publishing.
Technical verification does not override that acceptance result.

The user also approved direct Schedule placement beneath Project Master,
explicit Dashboard `N/A` presentation, PIP ownership of milestone definitions,
and the running-session persistence boundary. These decisions are recorded here
as an addendum, without rewriting the historical design or execution plan.

Investigation reproduced an apparent date loss at the input-acceptance boundary
and confirmed a separate Schedule visibility problem on Project re-entry. It did
not reproduce loss of an accepted canonical date. The exact text entered during
the original human session has not been supplied; the findings below distinguish
the demonstrated mechanisms from that unverified detail.

## 2. Binding decisions

### A. Project Workspace placement

Project Master remains visible at the top. The single Schedule presentation is
directly below it on Project entry: Official when no Draft exists, Working Draft
when one exists, or the legitimate no-Published/unavailable presentation.
Viewing that Schedule requires no second Open Schedule interaction.

Project Master is not a Resource. Resources retain the order Schedule, Team
Member, Weekly Report, AVL; the last three remain disabled and Migration pending.

### B. Current Published Dashboard values

An applicable Published date displays its existing formatted date. An applicable
null date displays `—`. A notApplicable Published occurrence displays `N/A`,
including when dates are stored on that occurrence. Empty/no-Published values
retain `—`. Full user-facing wording is `Not Applicable`, never
`not Applicability`.

Dashboard remains Current-Published-only. A2 visibility continues to depend on
at least one applicable Current Published A2 occurrence, not date presence.

### C. Milestone Definition ownership

PIP owns the canonical Milestone Definition Catalog and stable definition IDs.
Kevin/parser JSON is input for future mapping, not authority to create catalog
definitions. Parser/import implementation is outside this correction.

### D. Working Draft persistence

Every accepted edit persists immediately in `PrototypeState.schedules` through
the existing canonical command and reducer path. There is no Save Draft button.
Dashboard navigation and switching Projects within the same mounted application
must retain each exact ProjectId's Draft. Browser refresh, F5, browser closure,
and prototype restart are outside this in-memory persistence promise.

The detailed date-input treatment in section 4 is the recommended corrective
design submitted for human review here; it is not a claim that the user had
previously approved additional input formats.

## 3. Draft navigation persistence root cause

### Evidence and reproduction

Both worktrees passed the requested clean-baseline gate. Investigation used
unchanged production modules and existing tests; it changed no source, test,
fixture, or runtime data file.

Fresh existing regression command:

```powershell
npm run test:run -- src/scheduleWorkspace.spec.tsx src/legacy/characterization/runtime.spec.tsx
```

Result: 2 files / 41 tests / 0 failures. These tests already cover ISO edits,
null clears, applicability, navigation, and deliberately transient incomplete
text. Their success does not establish that rejected text is understandable to a
human; they do not require a visible editor error for that rejected text.

A separate read-only Node stdin probe bundled the production App into memory
with the installed Rolldown, then rendered it with JSDOM and React Testing
Library. An observing wrapper around the real `React.useReducer` recorded state
references and actions while forwarding every action to the actual reducer.
No replacement business reducer, fixture mutation, source patch, or probe file
was used. Fourteen scenarios exercised actual App buttons and input events:

| Input/action | Immediate canonical result | After navigation and reopening Schedule |
| --- | --- | --- |
| Kickoff Plan `2026-12-15` | one `scheduleReplaced`; ISO date stored | retained through Dashboard and through Nautilus |
| Kickoff Actual `2026-12-15` | one `scheduleReplaced`; ISO date stored | retained through both paths |
| Kickoff Plan/Actual `2026/12/15` | no action; previous canonical date retained | typed slash text replaced by previous date through both paths |
| Plan `2026-12-1` | no action; previous canonical date retained | previous date displayed |
| Actual `2026-02-30` | no action; previous canonical date retained | previous date displayed |
| Clear Plan to empty | one `scheduleReplaced`; `null` stored | empty field retained through Nautilus |
| Set applicability to `notApplicable` | one `scheduleReplaced`; value stored | retained through Nautilus |
| ID fix Actual `2026/12/15`, initially null | no action; canonical Actual remains null | field becomes empty after Dashboard return |
| ID fix Actual `2026-12-15`, initially null | one `scheduleReplaced`; ISO date stored | retained through Nautilus |

For all fourteen scenarios, the canonical state object after editing was the
same object throughout navigation. Official and Portfolio selector outputs
remained unchanged. Nautilus never displayed Manta's Draft. On every Manta
re-entry, Schedule was initially hidden until Open Schedule was clicked.

The ID fix slash-date case reproduces the visible symptom exactly: an entered
date is visible before leaving, then the field is empty on return. The editor is
`type="text"`; the probe found no `aria-invalid`, no `aria-describedby`, and an
empty native validation message despite the unaccepted text.

### Exact mechanism

**Root Cause:** In the reproduced date-disappearance cases,
`DateOnlyEditor.acceptText()` stores the entered string in component-local
`text`, but calls the canonical update callback only for empty text or a
successful `parseDateOnly()` result. The parser accepts a real, zero-padded
`YYYY-MM-DD` date, whereas Official/Portfolio display dates with slashes.
Slash-formatted, incomplete, or impossible dates are displayed without rejection
feedback and never dispatch `scheduleReplaced`. Leaving Workspace unmounts the
editor. Re-entry initializes it from the unchanged canonical DateOnly/null, so
the unaccepted text disappears. This is silent input rejection and lost
presentation text, not an observed reset of an accepted canonical Draft.

**Observed Boundary:** App owns one `useReducer(prototypeReducer, initialState)`
above the conditional Dashboard/Project Workspace branches. In-app navigation
preserves that reducer state, but unmounts Schedule presentation. Separately,
`openProject()` resets `activeResource` to `projectMaster`, and ProjectWorkspace
renders Schedule only when it equals `schedule`; therefore even a healthy saved
Draft is hidden on return until the redundant Open Schedule action.

**Corrective Principle:** Keep the existing canonical state owner and immediate
command/reducer persistence. Correct date acceptance and feedback at the editor
boundary, and show the canonical Schedule directly on Project entry. Do not add
storage, a Save operation, or another Draft owner to compensate for rejected or
hidden presentation state.

Source evidence at the investigated checkpoint:

- `src/scheduleWorkspace.tsx:51`: local text initialized from canonical value;
  `:57-64`: callback only for clear or successful parse; `:67-75`: text input
  and placeholder without rejection feedback.
- `src/domain/shared/dateOnly.ts:5,30,87`: ISO input pattern, calendar validation,
  and separate slash display formatter.
- `src/main.tsx:102,169-175`: fixture-backed initial value and sole App reducer;
  `:211-253`: command result to one replacement; `:373-387`: navigation only

- `src/application/state/prototypeReducer.ts:26`: same-ProjectId replacement;
  `src/application/selectors/scheduleSelectors.ts:284`: Draft read resolves the
  selected canonical Schedule, with raw DateOnly/null values.

## 4. Corrective architecture

### Compared approaches

| Approach | Assessment |
| --- | --- |
| A. Preserve one PrototypeState across view navigation | Required and already implemented/proven. Preserve it; introducing another provider/store would not correct the demonstrated failure. |
| B. Move the controller boundary that reinitializes state | No such reinitialization was found. Hoisting/restructuring the controller has no supporting evidence and adds risk. |
| C. Correct the existing editor acceptance and view presentation | Recommended. It addresses the observed failure boundaries while retaining commands, reducer, selectors, identities, and Published isolation. |

### Date acceptance contract proposed for correction

Retain a small date editor, with accepted formats shown as persistent help text,
not only a placeholder hidden by the current value:

- Accept complete `YYYY-MM-DD` and the application's existing display spelling
  `YYYY/MM/DD`. Only those two zero-padded, year-first formats are accepted.
- At the UI boundary, convert a complete slash spelling to hyphens, then use the
  existing `parseDateOnly()` calendar check. The canonical parser and DateOnly
  type remain unchanged. No locale-dependent parsing, `Date` conversion,
  ambiguous day/month input, or additional business/date-order rule is added.
- Every complete valid edit invokes the existing update callback immediately,
  without blur, Enter, Save, or navigation as a commit step. Canonical state
  contains only ISO DateOnly/null; subsequent remounts may display that canonical
  spelling rather than retaining the user's separator choice.
  Parsing makes input eligible for dispatch; only a successful canonical command
  makes it applied. Ownership/lifecycle failure retains the previous canonical
  value and the existing operation feedback, without claiming the edit was saved.
- Empty text immediately dispatches null. It is valid, including for empty
  Draft publication. Applicability changes never clear stored dates.
- Nonempty text that cannot parse remains transient while the editor is mounted.
  Mark it with `aria-invalid` and associate visible feedback through
  `aria-describedby`: `Date not applied. Enter a valid date as YYYY-MM-DD or
  YYYY/MM/DD.` The previous canonical value is unchanged.
- Keep that feedback visible for incomplete as well as impossible dates. Clear
  it when a complete valid value or empty/null is accepted. No success message
  may imply rejected text was saved.
- While a visible date editor has unapplied nonempty text, do not allow the
  Workspace Publish action to publish an older value behind it. Explain that
  the date must be corrected or cleared. This is a presentation guard against
  unaccepted input, not a new canonical Publish validation rule: pure commands
  still accept all structurally valid canonical Drafts, including null dates.
- Navigation and explicit Discard remain available. Unaccepted text is not
  promised persistence and can reset on leaving the editor; the visible error
  states that it was never applied. No second Draft cache preserves it.

Only raw editor text, input-validity feedback, catalog selection, and confirmation
presentation may be local UI state. No UI-local Schedule/Draft business object
is introduced. Editor text/feedback remains scoped by ProjectId, milestoneId,
and field and resets on identity changes; leaving the Draft clears any transient
validity summary. Removing a row also removes its transient error contribution,
so a removed editor cannot keep Publish blocked. The application controller
continues to dispatch only successful canonical command results.

This correction does not move `PrototypeState`, change its initializer, add a
reducer action, or alter lifecycle validation. Production fixture values remain
unchanged. Tests must observe canonical values and visible input feedback,
not merely that a DOM input accepts arbitrary text.

## 5. Project Master + direct Schedule presentation

The minimal Project Workspace order is:

```text
Project Master (existing Project data and Edit Project)
ScheduleWorkspace (exactly one instance, derived Official/Draft state)
Resources (Schedule / Team Member / Weekly Report / AVL)
Other existing feedback/content
```

Render the existing shared `ScheduleWorkspace` directly below Project Master on
every valid Project selection. Remove the resource condition that delays this
render. Remove the redundant Open Schedule button: the Schedule Resource card
becomes informational with the existing card styling and the text `Shown above`.
It does not open another copy, route, dialog, or Schedule state. No anchor/focus
machinery is necessary for this minimal treatment.

Project Master remains distinct from Resources and never owns Schedule data.
Only obsolete Schedule-selection presentation plumbing is eligible for removal;
do not redesign general navigation, dialogs, or other resources. Preserve the
`← Dashboard` control and exact ProjectId selection behavior. Create completion
and Review Existing enter this same shared Project Workspace path.

The Schedule instance derives its existing mode from canonical reads. A valid
Draft appears immediately, malformed Draft shows its existing unavailable/Discard
recovery, no Draft shows Official, and no Published remains legal. Changing
Projects resets transient editors and confirmations without changing either
Project's canonical Draft. Current Schedule, wherever shown, still means maximum
Published version only. No duplicate Official or Draft table is added to Project
Master or the Schedule Resource card.

## 6. Dashboard N/A semantics

The projection already carries each Current Published occurrence's canonical
applicability and formatted Plan/Actual values. Keep
`selectPortfolioDashboardRows()` Published-only and retain its contract. The
smallest formatting change belongs in `ScheduleValue` in
`src/portfolioDashboardTable.tsx`, where occurrences become visible cell content.

| Published occurrence / read | Cell presentation |
| --- | --- |
| applicable; Plan/Actual has a date | retain that field's existing formatted date and P:/A: presentation |
| applicable; Plan/Actual is null | that field displays `—` |
| notApplicable, whether dates are null or populated | a single `N/A` for that occurrence, replacing its date/status lines |
| no Published, zero-milestone Published, or no mapped occurrence | retain existing `—` |
| intentionally unmapped/placeholder column such as MDRR | retain existing placeholder behavior |
| unavailable read | retain existing unavailable state/tone/title; do not disguise it as N/A |

`notApplicable` has display precedence over its stored dates, but rendering must
not clear or rewrite them. Preserve occurrence identity and order when multiple
milestoneIds share one definition: one may display N/A beside another's applicable
date block; do not collapse them into one inferred value.

Use `Not Applicable` wherever the full Schedule applicability label is needed,
including Official and Draft labels; the Dashboard's compact occurrence is
`N/A`. Do not alter canonical enum values or introduce a new applicability state.

Leave `getPortfolioVisibleSchema()` and `hasApplicableA2()` unchanged. A2 is
visible if any Project's Current Published contains applicable A2 even with null
dates. Once visible, another Project's notApplicable A2 occurrence displays N/A;
a Project with no matching occurrence displays `—`. Working Draft A2 changes
cannot affect this calculation or Dashboard values before successful Publish.
Former A1 remains displayed as A; obsolete standalone A remains hidden.

## 7. Milestone Definition authority contract

PIP's existing authority is `src/config/v2/referenceData.ts`:

- `milestoneDefinitions` combines the canonical Portfolio definitions and MDRR;
- each definition has explicit stable `MilestoneDefinitionId`, `name` label,
  `stageGroupId`, `milestoneTypeId`, and `displayOrder`;
- `stageGroupCatalog` supplies the Stage display label by stable StageGroupId;
- active/review metadata, aliases, and `showInPortfolio` retain their existing
  meanings from `src/domain/schedule/milestoneCatalog.ts`.

Those explicit catalog seeds are authority, not values inferred from Project
demo fixtures or parser display names. Renaming a display label must not change
definition identity. `milestoneId` identifies a Project's milestone occurrence
and lineage, while `milestoneDefinitionId` classifies it. They are distinct.

Today App passes `milestoneDefinitions` into Workspace Add. The dropdown chooses
an existing definition ID; App allocates one occurrence ID per Add action; the
canonical command validates the reference. Duplicate definition use with distinct
milestoneIds remains legal. No free-text creation or existing-row definition
mutation is introduced.

The future authority boundary is only this contract:

```text
Weekly Report / PPT -> Kevin parser JSON -> mapping/resolution
                    -> existing canonical PIP MilestoneDefinitionId
```

Parser output cannot silently create, rename, or replace a canonical definition.
Unresolved input belongs to a later Import/Evidence decision boundary, such as
an unresolved candidate or Import Warning as specified by that future design.
This addendum defines no parser schema, mapping API, import entity, warning
implementation, catalog-management UI, or automatic catalog-mutation workflow.

## 8. Confirmation-state Minor correction

The existing independent `publishOpen` and `discardOpen` flags can both be true.
Opening Publish, opening Discard, confirming Discard, then starting another Draft
can show the old Publish confirmation because Discard closes only its own flag.
The earlier review verified no automatic publication or integrity bypass.

Use one mutually exclusive presentation choice: none, Publish confirmation, or
Discard confirmation. Opening one closes/replaces the other. Keep Editing and
either confirm action clear the presentation choice. Leaving Draft, changing
selected ProjectId, or leaving Workspace must clear it; starting a later Draft
must never inherit a previous confirmation. A failed command leaves canonical
state untouched and shows existing failure feedback, with the confirmation
closed and available for an explicit new attempt.

This state is presentation-only, not Draft identity or a third business mode.
Malformed Draft still permits Discard only. No Review workflow, Undo, or history
is introduced. Preserve explicit confirmation before either lifecycle operation.

## 10. Explicit out-of-scope

The future correction is limited to date-editor acceptance/feedback, direct
Project Workspace Schedule presentation, Published N/A formatting and full-label
wording, confirmation presentation state, fixture documentation consistency, and
tests for these behaviors. Exact implementation paths and TDD sequence belong
to a later human-authorized corrective plan, not this document.

Preserve the existing App state owner, canonical commands, reducer replacement,
Draft selector, Published selector, ProjectId and milestone identity, embedded
nullable Draft, immutable snapshots, structural validation, max+1/overflow,
externally supplied Publish timestamp, null versionNote, and atomic append/clear.

Do not add backend/DB/login, localStorage, IndexedDB, a Draft context/cache,
Save Draft, browser-refresh persistence, Parser integration, Import, Evidence,
Candidate, Proposal, Review workflow, rollback, history/version comparison, Team
migration, Weekly Report/AVL migration, legacy writes, Dashboard Draft reads,
Needs Attention logic, A/A2 visibility changes, production fixture changes, or a
general Workspace redesign. This is not Task 2.4 or whole-task closure.

## 11. Regression / acceptance criteria

The later corrective implementation must obtain behavioral RED for changed
behavior, then verify production paths through commands, reducer, and selectors.
Existing source and tests remain untouched during this design phase.

1. Enter Manta from Dashboard: Project Master appears first, exactly one Schedule
   presentation directly follows, and Resources retain their order. No Open
   Schedule click is required. Re-entry immediately shows an existing Draft.
2. In Plan and Actual, accept both complete approved date spellings, inspect the
   immediate canonical ISO value, then navigate through Dashboard and through
   Nautilus and return. Values survive without Publish or Save. Test initially
   populated dates and initially null dates, including ID fix Actual.
3. Clear dates to null and change applicability; each accepted action persists
   immediately and survives both navigation paths. Identity, unrelated Projects,
   and Published snapshots remain unchanged. No state initializer runs because
   of ordinary view navigation.
4. Incomplete, unsupported, and impossible dates show the unapplied-value error
   and accessible invalid state, emit no canonical update, and preserve the last
   accepted value. Correcting or clearing resolves the error. Invalid local text
   cannot be silently published; empty/null dates remain publishable. Leaving
   that editor may discard explicitly unaccepted text, never accepted state.
   Removing an invalid row clears its presentation error; command failure never
   produces an applied/saved claim or a canonical mutation.
5. Keep Manta Draft while opening Nautilus: Nautilus has only its own legal
   no-Published state or its own Draft. Return to Manta with no stale inputs,
   validation messages, catalog selection, or confirmations from another Project.
6. Dashboard/Current Schedule remain Published-only during Draft edits. After
   explicit successful Publish, new Current Published values appear and Draft
   clears atomically. Confirmed Discard retains old Published values; malformed
   Draft remains visibly unavailable and discardable.
7. Cover applicable date/null, notApplicable date/null, no Published, no matching
   occurrence, unavailable, placeholder, and duplicate-definition occurrences
   in Dashboard cells. N/A masks stored dates visually without deleting them.
8. With local test data, one Project's applicable A2 with null dates makes A2
   visible; another's notApplicable A2 displays N/A, and an absent value displays
   `—`. Editing only a Draft never changes A2 visibility. Preserve A mapping,
   Needs Attention, Project information, Team placeholders, filters, and Export.
9. Exercise Publish -> Discard -> confirm Discard -> start another Draft and the
   reverse overlapping-confirmation sequence. At most one confirmation is ever
   shown; none survives Draft exit, Project change, or Workspace exit. Keep
   Editing and failed commands do not mutate canonical state.
10. Catalog-backed Add, one caller ID allocation, duplicate-definition allowance,
    immutable existing classification, removal, max+1/overflow, failure
    non-mutation, Project Create/Create Anyway, and rename ownership still pass.
11. README accurately separates accepted demo topology from local edge-case test
    builders and disconnected predecessor fixtures. Parser authority contract
    remains documentation-only.
12. Run relevant component/runtime/Portfolio regressions, existing canonical
    lifecycle and Project/fixture regressions, full suite, build, diff check,
    authority scans, and fresh corrective review before a future implementation
    checkpoint. Then repeat human visual acceptance. Automated success alone
    does not close Task 2.3.

Human acceptance must use the in-app Dashboard control and Project selection in
one running application session. It should verify the actual entered date text,
visible validation feedback, immediate Draft return, and Published isolation.
Refreshing or restarting is a separate, intentionally unsupported persistence
boundary for this prototype.

## 12. Relationship to original Task 2.3 design and realigned plan

The historical files and commits remain unchanged. This addendum records the
new A/B/C/D decisions and proposed corrective detail for human review:

  gating and the realigned Slice 5 requirement to wait for Open Schedule. It
  changes presentation placement, not Project/Schedule authority.

  mapping target; it creates no import implementation scope.
- Decision D makes the running-session boundary explicit and retains the sole
  App reducer. The two previously deferred Minors become corrective design items.

This checkpoint authorizes only this new design addendum. Human review of the
written design comes next. Only after human approval may a separate corrective
implementation plan be written. No implementation, repair, final closure,
merge, push, or later task follows automatically from this design commit.
