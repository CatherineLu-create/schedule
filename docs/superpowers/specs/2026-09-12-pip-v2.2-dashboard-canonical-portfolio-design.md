# PIP V2.2 Canonical Portfolio Dashboard Design

**Status:** Approved direction — detailed architecture design for human review

**Date:** 2026-09-12

**Canonical baseline:** `46471b2b3d221f1724a2fc1bba1bb3bf9dbf3eaa` (`docs: plan Schedule Working Draft lifecycle`)

**Visual reference:** `D:\011schedule-dashboard-demo`

**Explicitly rejected implementation:** `ae3a5ce9ebce0a4f3b92069fcc14f07f4fadddab` (`feat: align V2.2 Dashboard presentation`)

## 1. Scope

This design replaces the rejected simplified Dashboard presentation with the information architecture and visual density of the approved old Dashboard demo. It combines:

- the old demo's page shell, Portfolio overview, three-card Needs Attention section, cohesive Search/Filters panel, and wide three-domain table; and
- the current PIP V2.2 canonical Project and Schedule authorities, exact `ProjectId` ownership, immutable Current Published Schedule semantics, current Project workflows, and current export behavior.

The old demo is a visual and information-architecture reference only. No old data, state, selector, identity fallback, Schedule logic, Team logic, worksheet conversion, or runtime module becomes part of the canonical application.

This design makes one deliberate read-boundary change: the Dashboard may project read-only Current Published milestone snapshots from `PrototypeState.schedules`. It does not add Schedule writes, Team reads, warning calculations, or Task 2.3 behavior.

## 2. Human visual decision

The target Dashboard is the wide Portfolio view represented by `D:\011schedule-dashboard-demo`:

```text
Project Information
Portfolio overview

Needs Attention
├─ Blocking Issues
├─ Milestone Due
└─ Overdue

Search / Filters

Projects
├─ Project Information
├─ Schedule
└─ Team
```

The old demo's grouped headers, horizontal density, compact rows, sticky Project context, white cards, slate canvas, and subtle domain colors are intentional parts of the target. This is not a generic restyling exercise.

The top-right labels will be `Export to Excel` and `+ Create Project`, matching the visual reference. They continue to invoke the current canonical export and Create Project callbacks; the labels do not authorize different behavior.

## 3. Why the previous parity attempt failed

The rejected checkpoint `ae3a5ce9...` was technically sound but solved the wrong problem. It polished the existing Project-only table, removed Project Status, and stopped at ten visible columns. It did not restore the old demo's Portfolio information hierarchy, Schedule stage groups, Team group, or wide-table density.

That checkpoint must not be merged or used as the implementation base. A future implementation of this design starts from canonical baseline `46471b2...`. The rejected diff may be consulted only for lessons about presentation tests and visual treatment.

## 4. Superseded Dashboard presentation contract

The human has superseded the earlier simplified Dashboard presentation target that specified:

- ten Project-only columns;
- no `Portfolio overview` subtitle;
- a single-domain `Project List`; and
- no Schedule or Team grouped columns.

The new target restores the old demo's three-domain Portfolio table and subtitle. This supersession applies only to Dashboard presentation and read integration. It does not supersede Project identity, state ownership, Project workflows, Schedule official-truth rules, Team gating, export semantics, or any Task 2.1/2.2 architectural decision not explicitly changed here.

## 5. Preserved canonical principles

### Project and Master

- `PrototypeState.projects` remains the sole canonical Project/Master authority.
- `ProjectId` is immutable identity and the only Dashboard row/navigation identity.
- Project name and QCI model name are display/search values, never identity.
- Create Project, duplicate Review, Create Anyway, Master Edit/Cancel, aliases, and hidden Master fields retain their current command/workflow/reducer paths.

### Schedule

- `PrototypeState.schedules` remains the sole canonical Schedule authority.
- Each canonical Project owns exactly one Schedule by exact `ProjectId`.
- Published versions are immutable Official Truth.
- Current Published is the maximum `versionNumber`, independent of array order and without a mutable current pointer.
- Working Draft is not implemented. Task 2.3 remains design/plan only.

### Team

- Team migration remains incomplete and the Workspace Team resource remains disabled with `Migration pending`.
- Although the current Project model and development fixtures contain `Project.team` values, this design does not approve a Dashboard Team read boundary. The Dashboard must not expose those values yet.

### Legacy and documents

- A source document is evidence/input, not Official Truth.
- The old demo and legacy runtime are not canonical authority.
- No old fake data, worksheet-derived rows, legacy Schedule JSON, or name-keyed Team map may enter the runtime.

## 6. New approved Current Published Portfolio read boundary

The Dashboard may now read Current Published Schedule milestones for read-only Portfolio presentation. This is an explicit, narrow exception to Task 2.2's previous Portfolio isolation:

```text
PrototypeState.projects ──ProjectId──────────────┐
                                                  ├─ canonical Portfolio read projection
PrototypeState.schedules ─Current Published only─┘
```

The projection must resolve Schedule ownership by exact `ProjectId`, use the existing `selectCurrentPublishedSchedule()` boundary, and consume only its `published` version snapshot. It must not read or infer from Working Draft, Candidate, Proposal, Review, Import, Evidence, predecessor commands, or legacy Schedule data.

This is not a new Schedule authority, cache, mutable Portfolio Schedule, or Draft read path. The existing Workspace official read remains unchanged.

The following remain explicitly inactive:

- `DashboardProjectRow.currentStage` derivation;
- `DashboardProjectRow.mdrr` derivation;
- Blocking Issues, Milestone Due, or Overdue calculation;
- Schedule-driven Needs Attention; and
- any Working Draft indicator.

The Schedule group's `MDRR` visual column is not permission to populate the existing unsupported Dashboard MDRR summary. Section 11 records its deliberately inactive behavior.

### Cell projection

For each Portfolio-enabled column, the selector retains every Current Published milestone whose `milestoneDefinitionId` equals the configured ID. Because canonical integrity permits more than one milestone with the same definition when `milestoneId` values differ, a cell must not arbitrarily choose first or last. It returns all occurrences in Published snapshot order, and the view stacks them compactly in that cell.

Each occurrence preserves `milestoneId`, `applicability`, `plan`, and `actual`. Dates use the existing `formatDateOnly()` presentation (`YYYY/MM/DD`) and appear as compact `P:` and `A:` lines. An applicable occurrence with a null date shows `—` for that line. A `notApplicable` occurrence shows `Not applicable`; if dates are present, they remain visible because canonical rules do not authorize destructive date normalization.

No matching milestone displays `—`. No name comparison, date fallback, fabricated value, or legacy record lookup is allowed.

## 15. Selector and read architecture alternatives

### Approach A — call the selected Schedule selector in the Dashboard component for every Project

The component could iterate projects and call `selectCurrentPublishedSchedule(state, projectId)` itself.

- **Authority safety:** potentially safe if it always uses the canonical selector.
- **Coupling:** poor; React would own Schedule-state interpretation and ID-to-column mapping.
- **Testability:** projection tests would require rendering the full Dashboard.
- **Draft leakage risk:** moderate; future component edits could bypass the official selector.
- **UI simplicity:** poor; branching and catalog grouping would live in JSX.
- **Performance:** repeated state scans during rendering.

This approach is rejected.

### Approach B — dedicated read-only canonical Portfolio selector

A focused selector joins canonical Project presentation and Current Published Schedule reads by exact `ProjectId`, producing a discriminated presentation model for the wide table.

- **Authority safety:** strong; it consumes `PrototypeState` but creates no state or cache.
- **Coupling:** explicit composition boundary; existing Project and Schedule domain selectors remain authoritative.
- **Testability:** Project mapping, Schedule states, exact ID mapping, duplicate occurrences, and row preservation can be tested without React.
- **Draft leakage risk:** low; all Schedule access flows through `selectCurrentPublishedSchedule()`.
- **Future Team integration:** Team can later receive a separate approved boundary without altering Schedule logic.
- **Performance:** adequate for the local prototype; implementation may compose selected reads per Project without inventing a repository/cache.

This is the recommended approach.

### Approach C — expand `DashboardProjectRow` with Schedule cells

The current Task 2.1 row could be made to carry Schedule presentation.

- **Authority safety:** possible, but the formerly Project-only type would conflate domains.
- **Coupling:** high; export and Project regressions would inherit Schedule concerns.
- **Testability:** Schedule failure could accidentally suppress a Project row.
- **Draft leakage risk:** higher as Task 2.3 evolves the Schedule shape.
- **Future Team integration:** encourages a single oversized mixed-domain DTO.

This approach is rejected. `DashboardProjectRow` remains Project-focused and retains unsupported `currentStage`/`mdrr` fields for existing behavior and export.

## 16. Recommended architecture

Create a focused application selector boundary, conceptually `src/application/selectors/portfolioDashboardRows.ts`, without modifying canonical state or domain models. Its planned public shape is:

```ts
interface PortfolioScheduleMilestoneOccurrence {
  readonly milestoneId: MilestoneId;
  readonly applicability: MilestoneApplicability;
  readonly plan: string;
  readonly actual: string;
}

interface PortfolioScheduleMilestoneCell {
  readonly milestoneDefinitionId: MilestoneDefinitionId;
  readonly occurrences: readonly PortfolioScheduleMilestoneOccurrence[];
}

type PortfolioCurrentPublishedRead =
  | {
      readonly kind: "unavailable";
      readonly issues: readonly ValidationIssue[];
    }
  | {
      readonly kind: "noPublishedSchedule";
    }
  | {
      readonly kind: "published";
      readonly versionLabel: string;
      readonly milestoneCount: number;
      readonly cells: readonly PortfolioScheduleMilestoneCell[];
    };

interface PortfolioDashboardRow {
  readonly projectId: ProjectId;
  readonly project: DashboardProjectRow;
  readonly category: string;
  readonly pcbNumber: string;
  readonly schedule: PortfolioCurrentPublishedRead;
}

function selectPortfolioDashboardRows(
  state: PrototypeState,
): readonly PortfolioDashboardRow[];
```

These are presentation read models, not canonical business entities. `plan` and `actual` are formatted for this read-only view. The future Task 2.3 editable Draft boundary must continue to retain `DateOnly | null` and is outside this design.

The selector:

1. starts from `selectDashboardProjectRows(state)` so canonical Project order and existing searchable/filterable values remain stable;
2. resolves Category and PCB# from the exact same `ProjectId` through a Project/Master-only lookup such as `getProjectById(state, projectId)?.master`, without consuming the `team` member returned by the broader existing `selectOfficialProjectSources()` shape;
3. calls `selectCurrentPublishedSchedule(state, projectId)` once for that row;
4. preserves the selector's unavailable/no-Published/published discriminant;
5. for a published result, groups raw immutable `version.milestones` by explicit `MilestoneDefinitionId`, formats dates, and preserves occurrence order; and
6. never consumes or exposes `Project.team` business values, Working Draft, legacy state, or a Project name as Schedule ownership.

The current `selectDashboardProjectRows()` implementation internally obtains its Project/Master values through `selectOfficialProjectSources()`, whose return type also carries `team`. The Portfolio composition must treat that extra member as unconsumed and must not forward it. Category/PCB# lookup uses the Project/Master-only path above so the new code does not widen Team coupling. A Team-only state change must leave every Portfolio Project/Schedule value and every Team placeholder unchanged.

The planned table metadata belongs in a presentation module keyed by stable milestone definition IDs. It may supply widths, group spans, sticky flags, and labels, but it must validate against the canonical catalogs and must not redefine milestone identity or lifecycle rules.

A focused `PortfolioDashboard` presentation component is preferred over growing `main.tsx` further. It receives projected rows plus `onOpenProject(projectId)`, `onCreateProject()`, and `onExport()` callbacks. `App` remains the state/command owner and the component owns only transient search, functional filter values, and column widths.

- `dashboardProjectsFromWorksheetRows`;
- old `DashboardProject` or `useState<DashboardProject[]>` authority;
- `schedule-output_3108.json`;
- legacy Schedule filters, warnings, version history, Working Draft, Publish, or row identifiers;
- old Team arrays/maps or worksheet data;
- `item.id || item.name` identity fallback; or
- old Create Project or Export implementations.

Safe reuse is limited to presentation observations and class-level ideas: spacing, radii, neutral palette, domain header colors, fixed widths, resize affordances, hover/focus treatments, and responsive grid breakpoints.

Static implementation audits must prove that canonical runtime imports no old demo or predecessor Schedule write module and that row navigation receives only `ProjectId`.

## 19. Accessibility, scrolling, and responsive behavior

- All buttons, filter controls, chips, resize handles, and project-open controls have visible focus styles and accessible names.
- Disabled filters use actual `disabled` attributes and explanatory text associated with `aria-describedby`.
- The Project name cell contains a keyboard-operable Open Project control using exact `ProjectId`; whole-row pointer activation may remain as a convenience but cannot be the only path.
- Table headers use semantic `<th>` elements and correct `scope`/group spans across all three levels.
- Domain colors supplement rather than replace text labels and borders.
- The shell and actions wrap at narrow widths; Needs Attention changes from one to three columns; filters use responsive one/two/three/five-column layout.
- The wide table keeps its minimum width and scrolls horizontally rather than hiding columns or shrinking text below readable size.
- Sticky header/columns must not cover focused controls and must use explicit backgrounds and z-index layers.
- Resizing respects minimum widths and does not change the data model.
- Empty result state appears inside the table card with the active result count and a clear `No projects match the current search and filters` message.

## 20. Export behavior

The visual Portfolio table and exported summary intentionally have different scopes.

The visual table contains Project Information, Current Published Schedule milestone presentation, and Team placeholders. The existing `Export to Excel` callback continues to export all canonical Project rows through the current `dashboardExportRow()` mapping, including its current Project/Master fields and fixed `Current Stage`/`MDRR` values. It does not respect visible search/filter results and does not add Schedule or Team columns.

This avoids silently changing a reviewed Task 2.1 behavior or claiming placeholder Team/Schedule presentation is an approved external data contract. Any future Portfolio export expansion requires its own explicit decision and tests.

## 21. Error and unavailable states

| Condition | Required Dashboard behavior |
| --- | --- |
| Project has no exact matching Schedule | Keep Project cells and navigation; show `Schedule data unavailable`; Schedule milestone cells `—`. |
| Project has duplicate Schedules | Keep Project cells and navigation; show `Schedule data unavailable`; do not choose one. |
| Selected row's Schedule is locally malformed | Keep Project cells and navigation; show `Schedule data unavailable`; do not partially render milestones. |
| Unrelated Project's Schedule is malformed | Only that Project row is unavailable; healthy rows remain readable. |
| Valid Schedule has no Published versions | Show `No published schedule`; milestone cells `—`. |
| Current Published has zero milestones | Show `Published vXX · No milestones`; milestone cells `—`. |
| Published milestone is `notApplicable` | Show `Not applicable`; preserve any present dates visibly. |
| Published milestone has null Plan/Actual | Show `—` for the corresponding P/A line. |
| Multiple milestones share one definition | Stack all occurrences in snapshot order; do not select arbitrarily. |
| Project field is null or catalog ID unresolved | Show presentation `—`; never fall back to legacy data. |
| No rows match search/filters | Keep Projects shell and headers; show explicit empty-result message. |

The selector issues may support diagnostics, but this design does not turn them into Needs Attention counts.
