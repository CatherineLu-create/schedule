Status: Design checkpoint for human review. Task 2.3 remains open; revised UI

## 1. Superseded decisions and preserved behavior

| Earlier requirement | Latest decision |
| --- | --- |
| Project Master → Schedule → Resources; Schedule card says `Shown above` | Project Master → Resources → Schedule; card says `Shown below`. The single Schedule remains directly rendered on Project entry without `Open Schedule`. |
| Free-text ISO/slash entry is the required primary Plan/Actual interaction, with persistent format help | A browser-native calendar is the primary interaction. Users can select a day without knowing or typing a format. The old text-field layout, ISO/slash help text, and slash-typing acceptance are no longer acceptance criteria for the new editor. |
| Empty text in the text editor dispatches canonical `null` | An explicit Clear action dispatches `null`. An empty value arising from an incomplete native keyboard edit or picker cancellation is not Clear. |

The earlier data-integrity rule remains: only a complete valid date is eligible
for an immediate canonical update; invalid or unapplied input never looks saved
and never silently permits Publish of a different value. Native keyboard use
may remain available as the browser provides it; it does not need a separate
slash-text adapter. The human decision does not authorize making the date input
`readonly` merely to suppress typing.

## 2. Project Workspace order

For every valid selected ProjectId, the page order is exactly:

```text
Project Master (existing data and Edit Project)
Resources (Schedule, Team Member, Weekly Report, AVL)
ScheduleWorkspace (one shared Official / Working Draft presentation)
Existing feedback and other content
```

`ProjectWorkspace` renders its existing single `ScheduleWorkspace` immediately
after the Resources section. The Schedule resource card remains informational,
with `Shown below` and no action that opens another view. Team Member, Weekly
Report, and AVL retain their disabled `Migration pending` treatment. The
`← Dashboard` control, Project Master editing, Create/Review Existing entry,
and exact ProjectId ownership remain unchanged. No tabs, router, second Schedule
table, or legacy resource path is added.

The shared Schedule instance still derives mode from canonical reads: Current
Published is read-only when there is no Draft, Working Draft appears when one
exists, and a Project with no Published Schedule keeps its legitimate empty
state. Malformed Draft recovery remains available. Moving the instance changes
DOM order only; it does not remount `App` or create another Schedule authority.

## 3. Calendar-first Plan and Actual

Use a small, enabled `<input type="date">` for each Draft Plan and Actual.
Keep the browser's visible native picker affordance usable by pointer and
keyboard. Provide a clearly labelled adjacent Open calendar button. It calls
`showPicker()` when available, synchronously inside its user-activated click
handler. Where that method is unavailable, focus the enabled input and retain
its own native picker affordance; verify that this still gives the user a
mouse-operable calendar. If the target Windows browser cannot open a usable
native picker, stop for a human product decision instead of adding a package
or custom calendar.

The input starts from the canonical `DateOnly` string or an empty string for
`null`. Opening the picker changes no business data and must not write today's
date. Moving between months or years also changes no canonical data. A selected
day supplies the native control's normalized `YYYY-MM-DD` string. Validate it
with the existing `parseDateOnly()` and pass the resulting `DateOnly` through
the existing `onUpdateMilestone` callback for that milestone and field. A
successful command/reducer replacement applies the value immediately to the
Working Draft. There is no Save Draft button. Closing or canceling without a
valid selection dispatches nothing and leaves the previous canonical value.

Place a separate button labelled `Clear Plan for …` or `Clear Actual for …`
beside the respective field. Only that explicit action passes `null` through
the same canonical update path. In particular, do not interpret a native
`input`/`change` event whose value is empty as Clear: some browsers can expose
an empty value while keyboard entry is incomplete. Keep the previous canonical
date until explicit Clear or a valid selection. If the visible editor has an
incomplete, invalid, or command-rejected value, give visible and accessible
`Date not applied` feedback, retain the existing Publish presentation guard,
and do not describe that value as saved. Repairing it with a valid selection or
explicit Clear resolves the guard after canonical props reflect the update.
An initially null field remains null when its picker is merely opened and
cancelled.

Associate each date control, picker trigger, Clear button, and error with an
accessible context identifying the selected Project, milestone occurrence,
and Plan versus Actual. Keep the control mutable and enabled in Draft mode;
Official Schedule remains read-only. Duplicate occurrences of one definition
must be distinguishable in their accessible row context. Native localized
display may vary, but canonical storage remains `DateOnly | null`. Read the
native string `value`, not `valueAsDate`, `valueAsNumber`, or a JavaScript
`Date`; introduce no timezone conversion or DateTime storage.

The [HTML Standard's Date state](https://html.spec.whatwg.org/multipage/input.html#date-state-(type=date))
requires a selected date value to be a valid date string. Its
[`showPicker()` contract](https://html.spec.whatwg.org/multipage/input.html#dom-input-showpicker)
requires a mutable control and transient user activation. [Chrome's browser
documentation](https://developer.chrome.com/blog/show-picker) demonstrates
the direct click handler and feature detection; [Mozilla's date-input
documentation](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/date)
describes the ISO `value` and browser-localized display. Edge 151 and Chrome
153 are installed on this Windows machine, but this documentation check is not
a test of the future application's picker or of the human's chosen browser.

## 4. Canonical lifecycle and isolation

`PrototypeState.schedules` remains the sole Schedule and embedded zero-or-one
Draft authority per ProjectId. Local UI state may hold only transient native
editor/feedback state, keyed to ProjectId, milestoneId, and field. The current
command → reducer path persists accepted Draft updates in the mounted app;
Dashboard and Project switching retain them, with no cross-Project leakage.
Refresh/restart persistence remains outside this prototype. No localStorage,
IndexedDB, backend, Draft cache, or Save action is added.

Current Schedule as official information and Dashboard/Portfolio continue to
read Current Published only. Selecting or clearing a Draft date does not alter
Published snapshots. Explicit Publish still revalidates and atomically appends
an immutable max+1 Published version while clearing Draft; Discard leaves
Published history unchanged. The existing exclusive Publish/Discard
confirmation state and its reset behavior remain intact. This input change adds
no Publish business-completeness rule. Published `notApplicable` still displays
`N/A` in Dashboard; applicable null, no-Published, and A/A2 visibility
semantics are unchanged. PIP retains Milestone Definition Catalog authority.

## 6. Required later verification and human acceptance

- Assert actual DOM and visual order Project Master → Resources → Schedule,
  exactly one Schedule Workspace, no `Open Schedule` prerequisite, `Shown below`,
  and three unchanged migration-pending resources. Cover Published, Draft, and
  legal no-Published presentations.
- Exercise both Plan and Actual with initially null and existing dates. Picker
  opening, month/year navigation, and cancellation must leave canonical state
  unchanged. A valid selected day must update the real Draft immediately;
  explicit Clear must update canonical `null`. Incomplete/invalid keyboard
  input must not dispatch `null`, appear saved, or allow silent Publish.
- Observe real command/reducer state across Dashboard and Project navigation.
  Verify exact ProjectId isolation, Published-only Dashboard and Current
  Schedule before Publish, and Publish/Discard plus confirmation reset after it.
- Perform a real interactive check in the human's target Windows browser:
  record browser and version, open the native calendar by mouse, navigate
  month/year, select a day, cancel without selecting, clear explicitly, and
  navigate away/back. Tests that only assign `input.value` do not prove that
  the native popup opens. Automated evidence does not replace final human
  acceptance. If that browser cannot support the approved mouse workflow,
  stop for a human decision before introducing a different picker.
- Run relevant focused regressions, the full suite, build, and diff checks in
  the later implementation phase. At the current baseline, historical full
  verification passed 47 files / 554 tests with `VITEST_MAX_WORKERS=2`;
  default seven-worker runs timed out in different runtime tests. The build
  passed with the known Vite over-500-kB warning. Do not report the default
  worker run as clean or change test timeouts/configuration for this design.
