# Task 2.2 — Schedule Official Read Runtime Migration Design

**Status:** Approved design; documentation only; not implemented

## Scope

Task 2.2 establishes canonical Schedule official-read authority in the
production prototype runtime. The read path is:

```text
selectedProjectId
    → canonical Schedule owned by that ProjectId
    → Current Published version
    → immutable Published milestone snapshot
    → read-only Workspace Schedule
```

This is intentionally not the complete Schedule migration. It introduces the
canonical ownership, integrity, fixture, query, and Workspace read boundaries
needed to display official Schedule truth. It does not implement Working Draft,
Import, Review, Publish, rollback, or any other Schedule write lifecycle.

Task 2.2 preserves the Task 2.1 Project/Master authority cutover. It does not
reintroduce legacy Dashboard Project state, whole-object Project selection, or
any second Project/Master authority.

## Context and repository reconciliation

At the Task 2.2 starting revision:

- `PrototypeState` contains only `projects`.
- The canonical `Project` TypeScript shape still embeds `schedule` and `team`.
- `ProjectSchedule` contains `publishedVersions` plus an optional
  `workingDraft`.
- `PublishedScheduleVersion` currently has a `ScheduleVersionId`, and its
  milestones use `MilestoneRowId`.
- `getLatestPublishedVersion()` currently returns the last array entry rather
  than the maximum version number.
- `createProject()` currently constructs an empty embedded
  `ProjectSchedule`.
- Task 2.1 initializes exactly five `canonicalProjectFixtures`, selects by
  `ProjectId`, and keeps Schedule and Team visible but disabled as Migration
  pending.
- Legacy Schedule JSON, React components, filters, edit state, version-history
  helpers, and mutation code remain physically present, but the canonical
  Task 2.1 Workspace cannot enter them.

These facts are migration inputs, not target semantics. Task 2.2 deliberately
replaces the embedded/last-entry/extra-ID read model with the approved separate
Schedule collection and official-read rules below. At the Task 2.2 completion
boundary, the canonical `Project` shape stored in `PrototypeState.projects`,
returned by Project creation, and accepted by canonical reducer actions must
not contain Schedule business state. If a predecessor-only type still embeds
Schedule so disconnected code can compile, that type must be explicitly
legacy-only and must not enter canonical state, command results, or reducer
actions.

The current legacy Schedule table displays Phase, Stage, Milestone, Plan, and
Actual. Repository inspection also shows that the canonical milestone catalog
has `stageGroupId`, `milestoneTypeId`, and `displayOrder`, while the current
Published milestone model has a milestone-definition reference,
`applicability`, `plan`, and `actual`. There is no canonical field that
faithfully represents the legacy `section`/Phase value as a separate business
concept. Task 2.2 therefore does not add a Phase field or infer one from a
different catalog. If the existing table shell retains a Phase presentation
column, its value is unsupported and must be shown as `"-"`; it is never read
from legacy Schedule data. Stage and Milestone labels come from the existing
V2 milestone reference data.

## Binding V2 principles

The following established principles remain binding:

- `ProjectId` is immutable; Project and milestone display names are not
  identity.
- Project/Master remains canonical current saved state. Master is not
  versioned.
- Team remains canonical current saved state. Team is not versioned.
- Schedule belongs to a Project and has a different lifecycle from Master and
  Team.
- Published Schedule versions are immutable official snapshots.
- A later Schedule design may add one optional Working Draft.
- Working Draft data cannot pollute official Portfolio or Workspace Published
  truth.
- Document is not Official Truth. The future write lifecycle remains Evidence
  → Candidate → Proposal → Review → Publish.
- No Provider, store, repository, service, persistence, API, or backend layer
  is introduced without a separate approved design.

## Goals

Task 2.2 must:

1. Add a separate canonical Schedule collection to `PrototypeState` while
   preserving `PrototypeState.projects` as the sole Project/Master authority.
2. Give every existing Project exactly one Schedule resource keyed by its
   immutable `ProjectId`.
3. Represent a valid Schedule with no Published history as an existing
   Schedule whose `publishedVersions` is empty.
4. Derive Current Published through one canonical maximum-version-number rule.
5. Model Published version and milestone identity without `ScheduleId`,
   `VersionId`, or a mutable current pointer.
6. Preserve Published snapshots as readonly official data with no direct
   mutation path.
7. Initialize runtime Schedule state from explicit canonical Schedule
   fixtures, never from a live legacy conversion.
8. Enable a canonical, official, read-only Schedule resource in Workspace for
   the selected `ProjectId`.
9. Initialize exactly one empty Schedule atomically with every successful new
   canonical Project.
10. Detect malformed canonical Schedule states rather than normalizing or
    disguising them as valid empty business states.
11. Keep Portfolio, Team, and all Schedule write behavior outside this task.

## Non-goals and forbidden shortcuts

Task 2.2 explicitly excludes:

- legacy Schedule authority, a live legacy adapter, or dual Schedule authority
- a `ScheduleId`, `VersionId`, or `currentPublishedVersionId`
- Project name, milestone name, or array position as business identity
- direct Published mutation or replacement of an existing Published snapshot
- Working Draft, Create Draft, Edit Schedule, Publish, or rollback behavior
- Evidence, Candidate, Proposal, Review, or Import behavior
- historical-version selection or a version-history UI
- Team migration
- Current Stage derivation
- MDRR derivation
- Milestone Due activation
- Needs Attention activation
- any other Portfolio behavior change
- a Provider, store, repository, service, adapter framework, or backend
  architecture
- fabrication of Published data for every development Project
- mass deletion of disconnected legacy Schedule code
- Task 2.3 or any later migration work

Rollback remains a future operation that publishes a new version. It is not a
pointer change to an older snapshot.

## Target ownership architecture

### Root canonical state

The target runtime state is conceptually:

```text
PrototypeState
├─ projects[]   canonical Project/Master authority
└─ schedules[]  canonical Schedule official-read authority
```

The collections are related by `ProjectId`, but their business state is not
duplicated. Project/Master remains current, non-versioned state. Schedule owns
Published immutable history and may be extended by a later approved task with
an optional Working Draft.

The canonical Project stored in `projects` does not embed a Schedule copy. The
separate `schedules` collection is not merely preferred by selectors; it is the
only canonical representation of Schedule business state.

The canonical Schedule collection is reducer-owned application state, not a
React component cache or presentation projection. A Schedule row/view model
may derive display values, but it cannot become writable business state.

### Schedule resource identity and ownership

Each Project has exactly one Schedule resource. Schedule has no independent
`ScheduleId`; its ownership key is `ProjectId`:

```text
ProjectId → one canonical Schedule
```

The invariant applies in both directions:

- every canonical Project has exactly one Schedule entry;
- every Schedule entry references one existing canonical Project;
- two Schedule entries cannot use the same `ProjectId`;
- a Schedule cannot reference a nonexistent Project.

Project rename and Project Master edits do not affect Schedule ownership.
Project names are never used to look up, join, or repair Schedule data.

### Empty Schedule representation

A valid existing Project with no Published Schedule has one Schedule entry:

```text
{
  projectId,
  publishedVersions: []
}
```

There is no second valid representation in which the Schedule entry is
missing. For an existing Project, a missing Schedule is an integrity failure,
not the business state “No published schedule.” Read logic must not manufacture
the missing entry.

## Canonical official-read model

The following shape is the semantic target. Exact source filenames and symbol
names are implementation-plan concerns, but the fields and identity rules are
not optional:

```ts
interface CanonicalProjectSchedule {
  readonly projectId: ProjectId;
  readonly publishedVersions: readonly CanonicalPublishedScheduleVersion[];
}

interface CanonicalPublishedScheduleVersion {
  readonly versionNumber: ScheduleVersionNumber;
  readonly versionNote: string | null;
  readonly publishedAt: string;
  readonly milestones: readonly CanonicalPublishedScheduleMilestone[];
}

interface CanonicalPublishedScheduleMilestone {
  readonly milestoneId: MilestoneId;
  readonly milestoneDefinitionId: MilestoneDefinitionId;
  readonly applicability: MilestoneApplicability;
  readonly plan: DateOnly | null;
  readonly actual: DateOnly | null;
}
```

`versionNote` and `publishedAt` are retained because the existing Foundation
already treats them as immutable publication metadata. They are not identity,
do not choose Current Published, and do not imply that Task 2.2 implements a
Publish command. The Task 2.2 Workspace is required to expose the current
version number and milestone snapshot; displaying the note or timestamp is not
required.

The target does not contain `workingDraft`, `ScheduleVersionId`,
`MilestoneRowId`, or Draft-specific metadata. Existing disconnected types may
remain physically present for predecessor tests or later migration work, but
they cannot back the Task 2.2 canonical runtime read.

### Published version identity

A Published version is identified by:

```text
(ProjectId, versionNumber)
```

`versionNumber` is a positive safe integer, consistent with the existing
`ScheduleVersionNumber` constructor. It must be unique within one Project's
Schedule. It need not be contiguous; `[1, 3]` is valid, and version 3 is
Current Published.

UI labels such as `Published v01` are formatting only. A padded display label
is never persisted or used for identity.

### Current Published rule

Current Published is derived as the version with the maximum
`versionNumber`. No current pointer is stored. Array order does not affect the
answer, and Workspace does not repeat the maximum-selection logic.

The maximum rule has one canonical implementation in the Schedule read
boundary. Any retained official-source selector that exposes Published
Schedule data must delegate to that same rule and to the separate canonical
Schedule collection; it may not continue using embedded `Project.schedule` or
the old last-array-entry helper.

### Published immutability

Published versions and their milestones are readonly snapshots. Task 2.2 adds
no action, command, form, or component callback that edits, deletes, reorders,
or replaces an existing Published snapshot. Initial fixtures and empty
Schedule creation are the only Schedule state materialization required here.

Future changes must remain compatible with:

```text
Official Truth
    → Working Copy
    → Review
    → Publish
    → new immutable Published version
```

### Milestone identity

Every business milestone has an immutable `MilestoneId`. This is distinct from
`MilestoneDefinitionId`:

- `milestoneId` identifies the Project's continuing business milestone;
- `milestoneDefinitionId` classifies it using the canonical milestone catalog.

The business identity is:

```text
ProjectId + milestoneId
```

A snapshot occurrence is located by:

```text
ProjectId + versionNumber + milestoneId
```

Within one Published version, `milestoneId` must be unique. Reusing the same
`milestoneId` in different Published versions of the same Project is valid and
expected when it represents the same continuing milestone. The same raw
`milestoneId` value in another Project does not collide because ProjectId is
part of business identity.

Milestone display name is not identity. A newly created business milestone
gets a new ID. If a milestone is removed and a later milestone has the same
display name, the later milestone does not automatically inherit the removed
milestone's ID.

The current Foundation's `MilestoneRowId` values change between fixture
versions and therefore cannot be reused as Task 2.2 lineage identity. Explicit
canonical Schedule fixtures must assign stable `milestoneId` values across
versions where lineage exists.

### Milestone business fields and presentation

Repository inspection supports exactly these Task 2.2 Published milestone
business fields:

- `milestoneId`
- `milestoneDefinitionId`
- `applicability`
- `plan`
- `actual`

No Draft owner, Draft metadata, raw imported identity, findings, Evidence,
Candidate, Proposal, Review, Import, Publish-command, or rollback metadata is
added.

Presentation resolves the existing `milestoneDefinitionId` through
`milestoneDefinitions`:

- Stage uses the definition's `stageGroupId` resolved through
  `stageGroupCatalog`;
- Milestone uses the definition's display name;
- applicability remains explicit and is not inferred from missing dates;
- Plan and Actual use existing `DateOnly` formatting when present;
- missing Plan or Actual values use a presentation placeholder, not a
  persisted string.

The legacy Phase value has no approved canonical source and is not stored in
the milestone. The existing `milestoneTypeId` remains definition catalog data;
it is not relabeled as Phase or Stage to imitate legacy columns.

An unresolved `milestoneDefinitionId` prevents faithful display and is a
canonical Schedule integrity error for this read boundary. The UI must not
borrow a legacy label or use the raw ID as a business-name fallback.

### Milestone ordering

The existing milestone definition catalog already supplies an explicit
`displayOrder`. Task 2.2 preserves that established presentation sequence by
ordering resolvable Published milestones by their referenced definition's
`displayOrder`. When two milestones have the same `displayOrder`, their
relative snapshot array order is preserved. That position is presentation
order only and is never milestone identity. Task 2.2 does not sort by date,
name, status, or `milestoneId`.

If a future approved milestone kind is not governed by that catalog order, its
ordering semantics require a separate decision. Task 2.2 does not add a second
sequence field.

## Canonical fixtures

Production runtime initializes Schedule state from an explicit
`canonicalScheduleFixtures` collection conceptually equivalent to:

```text
canonicalScheduleFixtures → PrototypeState.schedules
```

The fixtures are authored data. They are not calculated at runtime from
legacy Schedule JSON, from `canonicalProjectFixtures[*].schedule`, or through
a live adapter. Existing repository Schedule content may be consulted once
while authoring equivalent canonical fixture values, after which only the new
fixtures are runtime authority.

The fixture set must maintain one Schedule for each of the five canonical
Projects and demonstrate at least:

1. a Project with one Published Schedule version;
2. a Project with no Published versions;
3. a Project with multiple Published versions;
4. Current Published resolving to the maximum version number even when fixture
   array order does not put it last;
5. non-contiguous version numbers remaining readable;
6. at least one continuing milestone retaining the same `milestoneId` across
   versions; and
7. a valid Published version containing zero milestones.

Published history is not fabricated for all five Projects merely to make the
Workspace look populated.

## Canonical integrity boundary

Canonical ownership and shape are validated without silently rewriting data.
Task 2.2 integrity validation is limited to the following ownership, identity,
reference, and version-shape failures:

- an existing Project has no Schedule entry;
- more than one Schedule entry uses the same ProjectId;
- a Schedule references a nonexistent Project;
- a version number is zero, negative, non-integer, or outside the existing safe
  integer constraint;
- two Published versions within one Schedule have the same version number;
- two milestones within one Published version have the same `milestoneId`;
- a milestone definition cannot be resolved by the canonical V2 milestone
  catalog.

Existing constructors may continue to enforce the declared opaque-ID and safe
integer shapes. Task 2.2 does not add date-relationship, applicability/date,
publication-timestamp, catalog-activation, completeness, due, or other
business-consistency validation. Any such rule requires separate approval.

The integrity boundary must not:

- pick an arbitrary duplicate;
- treat missing Schedule as empty Published history;
- manufacture a missing Schedule during read;
- discard malformed Published versions and continue with the rest;
- renumber or sort versions into apparent validity;
- change milestone IDs;
- fall back to legacy Schedule data.

Whole-state ownership validation reports duplicate and orphan Schedule
entries. A selected Schedule with missing, duplicate, invalid-version, or
invalid-milestone data yields a resource-level unavailable result. An
unrelated orphan or malformed Schedule is still an invalid state and must be
reported by integrity tests/validation, but it need not crash an otherwise
resolvable selected Project Workspace.

## Canonical read boundary

Task 2.2 introduces a thin, pure read boundary consistent with existing
selector conventions. It provides the capabilities conceptually represented
by:

```text
get Schedule by ProjectId, while detecting missing and duplicate ownership
get Current Published version by max(versionNumber)
get Current Published Schedule result for a selected ProjectId
```

These are capability descriptions, not forced symbol names. The implementation
plan must use repository-conventional names and explicit result types.

The Workspace-facing result must distinguish three states:

```ts
type CurrentPublishedScheduleRead =
  | { readonly kind: "unavailable"; readonly reasons: readonly unknown[] }
  | { readonly kind: "noPublishedSchedule" }
  | {
      readonly kind: "published";
      readonly version: CanonicalPublishedScheduleVersion;
    };
```

The illustrative `unknown[]` is not an approved error payload type; the later
implementation plan must use the repository's existing validation/error
conventions rather than inventing an exception hierarchy. The required design
property is the discriminated separation between integrity failure, valid
empty history, and a valid current snapshot.

The read boundary:

- receives canonical state and immutable `ProjectId`;
- returns `unavailable` with a Project-not-found integrity reason if that ID is
  absent from `PrototypeState.projects`;
- detects missing/duplicate Schedule ownership before returning data;
- validates the selected Schedule before choosing Current Published;
- selects maximum `versionNumber` without mutation;
- returns the original readonly Published snapshot or a readonly projection;
- contains no React, command, reducer, legacy-data, or state ownership logic.

Workspace consumes this boundary. It does not use array indexing, select a
version locally, or infer that `null` means both empty and invalid.

### Interaction with existing official Project selectors

Task 2.1's Dashboard must continue to show all canonical Projects and its
Schedule-derived fields must remain `"-"`. Schedule integrity must not cause a
Project/Master row to disappear.

`selectOfficialProjectSources()` must no longer expose the existing lossy
`PublishedScheduleVersion | null` member, because `null` cannot distinguish
valid no-Published history from Schedule integrity failure. It may either omit
Schedule from that Project-focused result or expose the same discriminated
Schedule-read result produced by the Task 2.2 boundary. If it exposes Schedule,
it delegates to the one lookup/current-version implementation. It must never
map `unavailable` to `null`/no-Published, continue reading an embedded
`Project.schedule`, or establish a second official-read contract.

## Project creation integration

The existing Task 1.7 `createProject()` command and Task 1.8 interpretation
remain the Project creation business authority. Task 2.2 does not add a second
Project command or a parallel Create flow.

When the real Create flow reaches a successful canonical creation result, one
canonical state transition must establish both postconditions:

```text
new Project with ProjectId
+ exactly one empty Schedule with the same ProjectId
```

The state transition is atomic at the reducer/application-state boundary. A
Project must not be committed without its Schedule, and Schedule creation must
not be a later best-effort effect. Failure of either ownership invariant means
neither addition is accepted.

This applies to ordinary Create and to the successful second command in Create
Anyway. Create Anyway continues to reuse the original immutable ProjectId,
complete Master input, QCI PM, and intended context except the explicit
duplicate override. It initializes one Schedule, not one per command attempt.
Rejected and review-required command results create no Project and no
Schedule.

Master replacement, including Project rename, does not replace, re-key, or
duplicate the Schedule. The Schedule continues to be found by the unchanged
ProjectId.

The implementation plan may choose the smallest repository-conventional action
shape that makes the successful state update atomic. It must not introduce an
orchestration framework, and the completed implementation cannot expose a
dual-authority or half-created intermediate runtime state.

## Workspace behavior

Task 2.2 changes the canonical Workspace resource availability to:

| Resource | State after Task 2.2 |
| --- | --- |
| Project Master | Enabled; remains the Workspace landing resource |
| Schedule | Enabled; canonical Current Published read-only view |
| Team | Visible, disabled, labeled Migration pending |

Dashboard row selection, successful Project Create, and Review Existing still
land on Project Master. Opening Schedule uses the existing
`selectedProjectId`; it never resolves by Project name and never stores a
second selected Project or Schedule as mutable authority.

Task 2.2 exposes only Current Published. There is no version selector,
historical-version navigation, Edit Schedule control, Draft entry point,
Publish action, rollback action, or mutation callback.

### Valid Published Schedule

When at least one valid Published version exists, Workspace derives the
maximum-version snapshot and displays:

- a presentation label such as `Published v01`;
- the snapshot's milestones in the approved canonical display order;
- canonical Stage and Milestone labels;
- applicability and Plan/Actual values without edit controls.

### Valid Schedule with no Published versions

For an existing Schedule with `publishedVersions: []`, Workspace shows an
explicit business empty state equivalent to:

```text
No published schedule
```

It does not create fake version zero, placeholder milestones, or a Published
record.

### Published version with zero milestones

A valid Current Published version can contain `milestones: []`. This is
different from having no Published history. Workspace shows both the version
identity and an empty milestone-content state equivalent to:

```text
Published v01
No milestones
```

### Canonical integrity failure

Malformed canonical Schedule data produces an explicit non-business error
state equivalent to:

```text
Schedule data unavailable
```

The UI does not relabel the error as “No published schedule,” fall back to
legacy data, or guess a repair. When the failure is isolated to Schedule, the
Project Master resource and surrounding Workspace remain usable.

## Legacy isolation

Legacy Schedule code and data may remain on disk. The enabled canonical
Workspace Schedule must not depend on:

- `schedule-output_3108.json` or another legacy Schedule authority;
- app-global legacy Schedule arrays or version history;
- legacy selected-project-name joins;
- legacy Schedule selectors;
- legacy Schedule edit state or mutation actions;
- Working Draft React state;
- a live legacy-to-canonical converter.

A legacy React component may be reused only if it is genuinely
presentation-only after the change:

```text
canonical readonly props → presentation component
```

If a component imports legacy data, selects legacy state, owns Schedule
business state, invokes mutations, or infers identity, it is not an acceptable
canonical boundary. Local UI-only state such as an expanded row is not
Schedule authority, but Task 2.2 does not require new presentation features.

## Portfolio isolation

Task 2.2 does not activate any Schedule-derived Portfolio behavior. The Task
2.1 results remain unchanged:

- Dashboard Current Stage is `"-"`;
- Dashboard MDRR is `"-"`;
- Needs Attention is the canonical-safe empty state;
- Dashboard and Export continue to use the existing canonical Project row
  projector;
- Working Draft data cannot influence official Portfolio truth.

Having canonical Current Published data available is not itself approval for a
Portfolio derivation rule. Current Stage, MDRR, Milestone Due, warnings, and
attention behavior require later explicit designs.

## Error and edge-case behavior

| Case | Required behavior |
| --- | --- |
| Requested ProjectId is absent from canonical Projects | Return unavailable with a Project-not-found reason; Task 2.1 selection cleanup returns the UI to Dashboard without stale Workspace data. |
| Selected Project has exactly one valid Schedule and no versions | Show `No published schedule`. |
| Selected Project has one valid version | Show that version read-only. |
| Selected Project has multiple valid versions | Show the maximum `versionNumber`, independent of array order. |
| Version numbers are non-contiguous | Read the maximum deterministically; do not renumber. |
| Current Published has zero milestones | Show its Published label plus `No milestones`. |
| Existing Project has no Schedule | Show `Schedule data unavailable`; report integrity failure. |
| Duplicate Schedule entries use one ProjectId | Choose neither; show unavailable for that Project and report failure. |
| Schedule references no Project | Report an orphan integrity failure; do not attach it by name. |
| Version number is non-positive or invalid | Do not discard the version; the selected Schedule is unavailable. |
| Duplicate version numbers exist | Do not use array position to choose; the selected Schedule is unavailable. |
| Duplicate milestone ID occurs inside one version | The selected Schedule is unavailable. |
| Same milestone ID occurs across versions | Valid lineage when ProjectId is the same. |
| Same milestone display name uses a different milestone ID | Treat as distinct identity; do not merge by name. |
| Milestone definition is unresolved | Do not use legacy/raw labels; the selected Schedule is unavailable. |
| Project is renamed | Schedule continues to resolve by the same ProjectId. |
| Project Create is rejected or review-required | Add neither Project nor Schedule. |
| Project Create completes | Add one Project and one empty Schedule atomically with the same ID. |
| Create Anyway completes | Add one Schedule using the originally allocated ProjectId. |
| Team is opened | Control remains disabled and Migration pending. |
| Workspace opens | Project Master remains the landing resource. |

## Testing strategy

Task 2.2 uses the repository's existing Vitest and React Testing Library
reality. This section defines required behavioral layers, not implementation
steps or test file names.

### 1. Canonical ownership and integrity tests

Focused domain/state coverage proves:

- every canonical Project has exactly one canonical Schedule;
- duplicate ownership is invalid;
- an orphan Schedule is invalid;
- a missing Schedule is invalid and is not equivalent to empty history;
- Project rename leaves Schedule ownership unchanged;
- successful Project creation initializes exactly one empty Schedule;
- the empty Schedule uses the exact new ProjectId;
- rejected/review-required Create initializes no Schedule;
- Create Anyway still uses the original ProjectId and produces no duplicate
  Schedule;
- the Project/Schedule addition is atomic; and
- no embedded or legacy Schedule collection remains a second runtime
  authority.

### 2. Current Published selection tests

Focused read-boundary coverage proves:

- no Published versions returns the valid no-Published result;
- one version returns that version;
- multiple versions return the maximum version number;
- maximum wins regardless of array order;
- non-contiguous versions remain deterministically readable;
- zero version is invalid;
- negative version is invalid;
- non-integer/unsafe version values are invalid at the canonical boundary;
- duplicate version numbers are invalid; and
- no mutable current pointer or VersionId participates in selection.

### 3. Milestone identity and projection tests

Focused domain/read projection coverage proves:

- `milestoneId` is unique within one Published version;
- the same `milestoneId` is valid across versions of the same Project;
- fixture lineage preserves at least one ID across versions;
- milestone identity does not depend on display name;
- same-name milestones with different IDs remain distinct;
- `milestoneDefinitionId` is classification rather than business identity;
- unresolved definitions are reported rather than supplied from legacy data;
- Stage and Milestone resolve from the existing V2 definitions/catalogs;
- applicability and nullable dates retain their canonical meaning;
- explicit catalog `displayOrder` controls presentation order;
- equal catalog display-order values preserve snapshot array order without
  making array position identity; and
- no date/name/status/ID sorting rule is invented.

### 4. Canonical fixture tests

Fixture coverage proves:

- one and only one Schedule exists for each of the five canonical Projects;
- the fixture set contains no orphan or duplicate owner;
- Published, no-Published, multiple-version, non-contiguous/current-max,
  cross-version lineage, and zero-milestone scenarios are all present;
- fixture data is explicit rather than calculated from legacy data at runtime;
  and
- no Published data was added merely to populate every Project.

### 5. Workspace runtime tests

Behavioral tests prove:

- Project Master remains the landing resource;
- Schedule is enabled;
- Team remains visible, disabled, and Migration pending;
- Schedule follows `selectedProjectId` across at least two Projects;
- Project rename does not break the Schedule association;
- Current Published is read-only;
- no version-history selector exists;
- no Schedule edit, Draft, Publish, or rollback action exists;
- no-Published and zero-milestone states are visibly distinct;
- integrity failure is visibly distinct from valid empty history;
- a Schedule integrity failure does not unnecessarily crash Project Master;
- Current Published display ignores version array order;
- displayed milestones use canonical data/reference labels only;
- canonical Workspace does not require legacy Schedule authority; and
- an absent selected Project returns unavailable from the read boundary while
  existing Task 2.1 cleanup prevents stale Workspace rendering.

### 6. Task 2.1 and regression verification

Regression coverage must preserve:

- exactly five initial canonical Projects;
- canonical Project/Master Dashboard projection;
- ProjectId selection;
- ordinary Create, required rejection, duplicate review, and same-ID Create
  Anyway behavior;
- Project Master Edit and alias behavior;
- Dashboard Current Stage and MDRR as `"-"`;
- canonical-safe empty Needs Attention;
- Export over all canonical Project rows;
- Team Migration pending gating; and
- all existing Foundation behavior outside the intentionally replaced embedded
  Schedule read semantics.

Final implementation verification must include focused Task 2.2 tests, the
full regression suite, and the production build.

## Expected design-level module boundary

Task 2.2 is expected to touch only the smallest existing layers needed for the
approved authority migration:

- shared/domain Schedule identities and the official Published read model;
- Schedule integrity and current-version domain/read rules;
- `PrototypeState` and reducer actions needed to own Schedules and atomically
  initialize one with a new Project;
- explicit V2 canonical Schedule fixtures;
- application Schedule selectors/read results;
- existing official Project-source integration where necessary to eliminate
  the embedded Schedule rule;
- `src/main.tsx` Workspace resource wiring and a narrow canonical Schedule
  read-only presentation boundary; and
- focused domain, selector, state, fixture, and runtime tests.

The implementation must retire the embedded `Project.schedule` member from the
canonical Project type used by state, Project creation results, and reducer
actions, and update affected fixture/test construction so there is one
Schedule authority. A predecessor-only embedded type may remain only in
disconnected legacy code. This requirement is part of the ownership cutover,
not a license to redesign Project/Master, Team, commands unrelated to Project
creation, or Schedule write workflows.

Task 2.2 does not create a Provider/store/repository/service layer. It does not
move unrelated UI or perform mass legacy cleanup.

## Migration sequencing constraints

A later implementation plan must preserve these boundaries:

1. Establish the target official-read identity, integrity, and current-version
   rules with focused tests before wiring the Workspace.
2. Author explicit canonical Schedule fixtures and prove the one-to-one
   Project ownership invariant.
3. Add `PrototypeState.schedules` and atomic Project-plus-empty-Schedule
   creation without leaving an externally reviewable dual-authority state.
4. Redirect every active official Schedule read away from embedded Project and
   legacy state to the one canonical Schedule boundary.
5. Enable the read-only Workspace Schedule only after valid, empty, and
   unavailable states are distinguishable.
6. Keep Team gated and leave Portfolio derivations unchanged.
7. Verify legacy isolation, full regression, and production build before any
   checkpoint commit.

No implementation slice may end with both embedded `Project.schedule` and
`PrototypeState.schedules` acting as writable or official-read authorities.

## Success criteria

Task 2.2 is complete only when:

1. `PrototypeState.schedules` is the sole canonical Schedule runtime
   authority.
2. `PrototypeState.projects` remains the sole Project/Master authority.
3. Canonical Projects, Project creation results, and canonical reducer actions
   contain no embedded Schedule business state.
4. Every existing canonical Project has exactly one Schedule keyed by
   `ProjectId`, with no duplicate or orphan entries.
5. Missing Schedule and empty Published history are distinct states.
6. A valid no-Published Schedule is represented only by
   `publishedVersions: []`.
7. Schedule has no independent ID and Project names are never Schedule
   identity.
8. Published version identity is `(ProjectId, versionNumber)` with positive,
   unique version numbers.
9. Current Published is derived only by the canonical maximum-version-number
   rule, independent of array order and contiguity.
10. No VersionId or current-version pointer participates in canonical reads.
11. Published snapshots have no direct mutation path.
12. Milestones use immutable `milestoneId` lineage, unique within a version and
    reusable across versions of the same Project.
13. Milestone names are never identity.
14. Canonical Schedule fixtures cover Published, no-Published,
    multiple/non-contiguous version, retained lineage, and zero-milestone
    cases without fabricating history for every Project.
15. Successful Project creation atomically initializes exactly one empty
    Schedule with the same ProjectId.
16. Create Anyway still uses the original ProjectId and creates no duplicate
    Schedule.
17. Workspace keeps Project Master as landing, enables Schedule as canonical
    official read-only, and leaves Team disabled as Migration pending.
18. Current Published, no-Published, zero-milestone, and integrity-error UI
    states are distinct.
19. Workspace exposes no history selector or Schedule write action.
20. Canonical Workspace Schedule has no live dependency on legacy Schedule
    authority, state, name joins, selectors, edit state, or mutations.
21. Dashboard Current Stage and MDRR remain `"-"`, and Needs Attention remains
    canonical-safe empty.
22. No Working Draft, Import, Publish, rollback, Portfolio, or Team behavior is
    added.
23. No Provider/store/repository/service/backend architecture is introduced.
24. Focused Task 2.2 tests, the full regression suite, and the production build
    pass.

This document records the approved Task 2.2 design. It does not authorize
implementation, staging, committing, or writing the implementation plan.
