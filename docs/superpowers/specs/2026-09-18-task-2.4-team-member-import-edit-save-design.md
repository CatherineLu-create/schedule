## 3. Canonical Team 與最小資料邊界

唯一已儲存 Team authority 是精確 ProjectId 對應的 Project.team，位於 PrototypeState.projects；不新增 PrototypeState.teams、Provider、repository、service 或全域 Team cache。讀取目前 Team 從 canonical Project 取得，Save 重新按 ProjectId 讀取當下 Project，執行完整驗證，成功後以一個 projectReplaced 更新同一 Project，保持 id、master、identityAliases 與 schedules 不變；失敗不 dispatch。Team 是 current saved state，無 Publish。

ProjectTeam 現有 projectRoles 三個單值槽位、functions、appliedTemplate；ProjectRoleAssignment／FunctionPersonAssignment 目前只有 ID、姓名、Email，Function assignment 角色只有 leader／owner／member。它不足以保存多位待修正的受限角色、來源 Function 原文、隱藏電話及任意附加欄，也不能把未知角色安全地塞成 member。建議以兩層處理：
- **暫存候選列**：每列保留檔名、sheet、原列號、原欄索引／表頭／值、原 Function、辨識出的角色或「未分類」、姓名、Email 與修正狀態。多位候選在此完整可見，不先壓進單值 projectRoles。
- **單一 canonical Team 的必要擴充**：成功 Save 時，ProjectTeam 的人員 assignment 保留原 Function 標籤、附加欄與來源列參照；無法安全判定 Owner／Leader／Member 的資料保留明確「未分類」內部狀態及原文，不冒充 member。精確重複列可對應一筆有效 assignment，但其來源列參照須全數保留。可用既有 standard/custom Function ref；非標準 Function 以原文 custom ref 保存，不改中央 catalog。實作時避免同時保存兩份可分歧的 roster；任何衍生投影都從 Project.team 計算。

Team Template 結構和各 Project 名單分開。src/domain/team/teamTemplate.ts 的 updateProjectTeamFromTemplate 只補缺少的 standard Function；匯入不自動套範本、改範本不回寫既有 Project 人員。整份取代針對人員名單，不暗改原本的 template 版本、既有 Function 適用狀態，或把未列出的空白 template Function 判為 N/A；只有使用者針對衝突明確修正適用狀態時才一併儲存該狀態。新 custom Function 可有不依姓名產生的穩定 ID，不靜默加入 central catalog。

## 4. 匯入辨識、逐列保存與安全失敗

接受 CSV／XLS／XLSX。以各 sheet 的內容尋找 Function 與 Member 姓名欄及可辨識的 email 欄；工作表名稱、表頭位置、欄列順序、增減人員與字體／色彩／欄寬微調不作固定位置依賴。Member 是姓名欄，**不是** member 角色。實檔有 email 表頭但 92 筆人員列的 Email 都空白；個別 Email 缺漏可顯示 Advisory，不單獨阻擋 Save。只對實檔命名變體與已知原則加入有限、可列舉 alias，例如 `QCI-SW Bundle-Leader(Chrome)` 與 `QCI-SW Bundle -Owner-(Chrome)` 的分隔空白差異；一般清理限空白、明確安全的分隔符／大小寫差異，不刪廠區、QCI／QCMC、EE／EE ERD／EE IQC、Chrome／Windows 等有意義文字，不自由猜測七角色。

每個被辨識的人員列保留 Function 原文、姓名、Email、所有有資料的附加欄及來源位置；隱藏欄的資料仍須讀入和保存。來源儲存格的原值／型別也要可追查，尤其 E70 是數值電話，不可因一律假設文字而漏掉，也不可憑空補出 Excel 未保存的前置零。重複或空白表頭以欄索引區別，避免值互相覆蓋。畫面主要顯示 Function、姓名、Email、角色／問題，附加欄可在列詳情檢視和必要時修正；保留資料不等於重製 Excel 樣式。只有姓名、Email、電話與其他人員資料都空白的列才可當空白範本列，且不推定 N/A；Member 空白但 Email、隱藏 Tel. No. 或其他欄有資料的列須保留原列並標示可定位的資料不完整／歸屬疑義，要求修正或明確排除後才能 Save，不可靜默略過。只有實檔證實的合併欄或明確階層規則可承接 Function；有姓名而 Function 真正無法歸屬者是可定位的 Blocking，未知但原文完整的 Function 則保存為 custom，不強制完成全公司標準化。

若沒有符合格式的 sheet，回報可定位的表頭問題；若有多張符合格式，要求 PM 選一張，不自動合併。無法讀取、資料衝突、部分列／欄解析失敗，都不可產生「已部分成功」的可 Save 取代資料；保留既有 saved list 和先前未儲存編輯，供修正或重新選檔。取消選檔、匯入失敗、取消匯入同樣不清空任何既有資料。零筆有效人員或空檔不得由 Import 造成整份清空；若使用者透過逐列手動刪除而要儲存零筆，需有另外明確的清空確認，仍可 Save 七角色皆 0 人的合法狀態。

## 5. 七角色辨識、計數與驗證

| 唯一受限角色（已核准） | 本樣本 Function 字樣（安全 trim 後） | canonical 投影 |
| --- | --- | --- |
| QCI PM | `QCI-PM-Owner`（第 5 列） | ProjectTeam.projectRoles.qciPm |
| QCI PjM | `QCI-PJM-Owner`（第 6 列） | ProjectTeam.projectRoles.qciPjm |
| Acer PM | 未出現；只能由明確 Acer PM 標示或使用者確認，不能從 QCI／QCMC 推測 | ProjectTeam.projectRoles.acerPm |
| QCI-ME-Owner | `QCI-ME-Owner`（第 22 列） | 對應 Function 的 owner assignment |
| QCI-EE-Owner | `QCI-EE-Owner`（第 14 列） | 對應 Function 的 owner assignment |
| QCI-Thermal-Owner | `QCI-Thermal-Owner`（第 65 列） | 對應 Function 的 owner assignment |
| QCI-BIOS-Owner | `QCI-BIOS-Owner`（第 31 列；原值末尾有一個 ASCII 空白） | 對應 Function 的 owner assignment |

表中的 Excel 標籤與列號是實檔觀察；由已核准角色對應到 canonical 欄位是本輪**明示的設計映射**，不是「命名原則」工作表提供的現成對照。`QCI-PM-Leader`（第 4 列）仍是 Leader，不落入 QCI PM 的 Owner 人數限制。以上是精確角色身分，不是對任意字串找 PM、EE 或 Owner 子字串。現有 src/fixtures/v2/teamTemplateFixtures.ts 的 DEV Function 是開發資料，不自行當作企業 alias 表；實檔的「命名原則」也沒有給出標準 FunctionId。未核對的相似文字保留原文並列為待確認，不猜成受限角色。尤其 `QCMC-EE IQC-Owner` 的 6 列不計入 `QCI-EE-Owner`；EE ERD／EE IQC、廠區及平台字樣不得被正規化吞掉。

原文能明確標示其他單位的 Owner、Leader 或 Member 時，保留該角色和 Function 原文，多位仍合法；原文沒有足夠資訊時才標記「未分類」，不能因欄名 Member 就推成 member。七角色辨識優先於一般角色辨識，但一般辨識絕不可反向猜成七角色。

每個受限角色：0 位不同人員為聚合 Advisory、可 Save；1 位正常；超過 1 位不同人員可預覽和修正，但 Save Blocking。Excel 缺該角色列就是 0，系統不補假人員。其他 Function 的 Owner，以及所有 Leader／Member，不設人數 Blocking 或 Advisory；同一人兼不同角色各角色保留。未分類角色保留原文，不自動降成 Member。沒有 Email 的單列僅提醒；姓名相同不足以推論同一人。

同一 Function、同一角色、非空且正規化後相同的 Email，且姓名及所有其餘欄位一致，才可把重複來源列折為一位計數；來源列全部保留可追查。不同 Email 不因姓名相同合併；同 Email 但姓名／電話／附加欄衝突，不丟欄位，標示資料衝突並要求修正。同一人跨角色不跨角色去重。缺 Email 的多列即使同名也不自動去重；若影響受限角色是否超過一人，標示身分待確認並阻擋 Save 直到使用者明確處理，此阻擋來自無法判定人數而非缺 Email 本身。

既有 src/domain/team/teamValidation.ts 對所有 Function 發出 multiple-owners、multiple-leaders、missing-owner 的通用人數判斷，必須在匯入預覽、手動編輯、saveProjectTeam 與測試一起替換為上述七角色規則；不能只改 UI。現有 not-applicable-with-people 只在**明確** N/A 且有人時維持衝突；空白人員或缺列不等於 N/A。若匯入或編輯使既有 N/A Function 出現人員，問題摘要定位該 Function，提供僅針對此衝突的「改為適用」修正動作；在使用者明確執行前，Save 仍 Blocking，不刪人也不偷偷改狀態。修正留在編輯 buffer，Cancel 還原原本 N/A，Save 才與人員名單一併原子更新，同時保持 appliedTemplate 版本。這不是匯入必填欄或所有 Function 的新適用狀態填寫要求。現有 template 的 pending-applicability 可以維持非阻擋提示，但不新增「所有單位必填 Owner／適用狀態」門檻；未知 Function 不因不在 template 而漏人或被擋 Save。

| 現有通用判斷／資料處理 | 本次取代契約 |
| --- | --- |
| 所有 Function 多 Owner 即 Blocking | 只對四個指定 QCI Owner 角色計算不同人員；其他 Owner 不因人數產生問題。 |
| 所有 Function 多 Leader 即 Blocking | Leader 一律不設人數 Blocking／Advisory。 |
| Applicable Function 無 Owner 即 Advisory | 只有七個指定角色 0 人產生聚合提醒；其他 Function 不因 Owner 人數提醒。 |
| 只按同 assignmentId 去重 member | 按已確認的 Function／角色／非空 Email／其餘資料完整一致判斷重複，保留全部來源列；衝突不得吞掉。 |
| 空白、pending 與 N/A 的既有表示 | 空白範本列不算人也不等於 N/A；只有明確 N/A 且有人才衝突，pending 只可非阻擋提示。 |

## 6. 編輯狀態、Cancel 與原子 Save

| 狀態／動作 | 結果 |
| --- | --- |
| 進入 Project → Team Member | 按精確 ProjectId 顯示 saved Team 唯讀；無 saved Team 顯示空狀態。 |
| Edit Team | 從當下 saved Team 建立本地編輯 buffer；可改 Function、姓名、Email，新增／刪除人員列；可檢視保留的附加欄；若出現既有 N/A 與人員衝突，可明確修正該 Function 為適用。 |
| Import 選檔 | 非同步解析到隔離候選，不寫 saved Team，也不蓋掉既有編輯；可預覽與定位問題。 |
| 匯入候選確認 | 若已有未儲存編輯，先明示將取代目前編輯 buffer，提供 Stay／取消；確認後才把候選放入共用表格。 |
| Cancel 匯入／檔案選取取消 | 僅丟棄該次候選／選檔；先前編輯與 saved Team 均保留。 |
| Cancel 整份編輯 | 若有變更先提供 Stay 或丟棄確認；明確丟棄後返回 saved 唯讀，絕不呼叫 Save。 |
| Save | 重新核對 ProjectId、候選、七角色與所有 Blocking；成功只以一個 projectReplaced 更新 Project.team，Advisory 摘要仍可見；失敗保持編輯與 saved Team 原狀。 |

有 saved list 的 Import 在 Save 前必須有整份取代確認，顯示目標 Project、檔名、原有／新檔有效人員列筆數，並說明「新檔未包含的人不保留；系統內修改不自動合併」。筆數是列數，不宣稱唯一人數；如去重後筆數不同，另列重複來源列與有效人員數。一般手動 Edit 不每次跳整份取代確認。確認右側放 Import／Save／確認；左側放 Cancel／Back／Stay。

導航離開或切換 Project 且有未儲存編輯時，提供 Stay 或明確丟棄；不自動 Save、不默默套到另一 Project。每次實際選定檔案並開始讀取時帶入起始 ProjectId、編輯世代及操作識別，並使同一 Project 中較早的未完成讀取失效；只有目前有效的操作可交付候選。檔案讀取晚到時，若 Project 已切換、操作已取消／被較新讀取取代或世代不符，就丟棄結果而不覆寫任何 buffer。取消較新的讀取不會復活舊讀取；取消選檔不清空既有 buffer。成功 Save 只保證目前 prototype session 內重新進入可見；F5／關頁／重啟不保證保存。

## 8. 後續驗收案例

1. 改 sheet 名稱、表頭位置、欄列順序與視覺樣式後仍可辨識；多張符合時必須選 sheet，不能合併。
2. Member 姓名欄不被當作 member 角色；原 Function、隱藏 Tel. No.、額外欄和來源位置在 Save 後仍可查，主要畫面保持簡潔。
3. QCI PM／QCI PjM／Acer PM／四個 QCI Owner 各測 0、1、2 位：0 只提醒且可 Save，2 顯示兩列並擋 Save；缺列不補人。
4. QCMC、EE ERD、EE IQC、不同廠區、Chrome／Windows 不誤配；未知 Function 可保存原文與人員，不強制改 Member 或擴充 catalog。
5. 非受限 Owner、Leader、Member 可多人而無人數問題；同人跨角色保留兩個角色。
6. 同 Function／角色／Email 且其他欄位完全相同的列不重算人數，來源兩列可追查；同名異 Email 不合併；同 Email 欄位衝突可定位且不可靜默丟失。
7. 缺 Email 單列僅提醒；多列缺 Email 影響受限角色身分時要求明確處理，不能靠姓名猜。
8. 全空白範本列不算人、空白不等於 N/A；Member 空白但 Email／Tel. No. 有值的列保留並要求定位補正，不可靜默略過。既有 N/A 且新增人員時，明確「改為適用」才能解衝突；Cancel 恢復原 N/A，Save 保留 appliedTemplate 版本；template pending 不形成整份填寫門檻。
9. 選檔取消、無法解析、部分解析、零筆檔、取消匯入，均保留 saved Team 與既有未儲存編輯；手動清空需明確確認。
10. 已有編輯再選新檔，Stay 保留原 buffer；確認替換只替換本地 buffer；Save 前整份取代確認顯示 Project、檔名、原／新列數及不合併警語。
11. 手動小修改不用整份取代確認；Save 重新驗證，Blocking 無 reducer transition，Advisory-only 成功只替換同 Project.team。
12. 切 Project／導航與晚到 FileReader 結果不串案；同 Project 依序開始讀取 A、B，即使 B 先完成或取消，A 晚到也不能覆寫 buffer；取消整份編輯回到原 saved read，成功 Save 後同 session 重入可見。
13. Dashboard、QCI PM filter、Needs Attention、Project-only export、Schedule 與其 Published/Draft 行為不變。

## 9. 風險與未來預留

本輪已核對指定版本 Excel 的實際表頭、合併儲存格、隱藏欄及命名原則，但單一樣本不能證明 CSV／XLS、其他合法微調、多 sheet、衝突／重複 Email 或部分解析情境；後續須用合成資料驗收，不把未出現情境說成實檔事實。另一風險是目前 ProjectTeam 欄位不足、舊通用 validator 與舊 Team 表格斷線；後續須以端到端測試證明保存的附加資料及原子 Save，不可只通過 UI 預覽。

未來可能建立／修改 Team Member 範本、下載 Excel 範本、平台直接套用，以及透過公司 Outlook／人員目錄搜尋姓名。範本結構與 Project 名單分開，改範本不自動改既有 Project 人員；目錄選人不能取代 Excel 或手動填寫。這些只保留擴充邊界，本輪沒有假按鈕、目錄連線、權限設計、額外未使用欄位或通用框架；正式目錄及權限方案由 MIS 後續確認。
