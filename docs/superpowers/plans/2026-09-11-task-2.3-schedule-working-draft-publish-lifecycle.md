# Task 2.3 — Schedule Working Draft + Publish Lifecycle Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the canonical Schedule Working Draft lifecycle, editable milestone Draft UI, Cancel, and immutable max+1 Publish while preserving Task 2.2 Official Truth semantics.

**Architecture:** Working Draft remains embedded as zero-or-one mutable state inside the sole canonical Project Schedule. New canonical pure lifecycle commands create/edit/cancel/publish the Draft; reducer/application integration applies successful Schedule replacements atomically. Official Published reads continue ignoring Draft state, while a separate Draft selector serves the PM editing Workspace.

**Tech Stack:** React, TypeScript, Vite, Vitest, existing local canonical PrototypeState architecture.

**Spec:** docs/superpowers/specs/2026-09-11-task-2.3-schedule-working-draft-publish-lifecycle-design.md

**Terminology:** The required Architecture header's phrase “mutable state” means editable business state represented by readonly TypeScript values and changed only through immutable replacement transitions; it never authorizes in-place mutation.

## Global Constraints

- `PrototypeState.schedules` remains the sole canonical Schedule and Working Draft authority, and each existing Project owns exactly one Schedule.
- Working Draft is embedded in `CanonicalProjectSchedule` as the required property `workingDraft: CanonicalScheduleWorkingDraft | null`. There is no separate `scheduleDrafts` collection, Draft map, cache, or component-owned Draft business object.
- Canonical `Project` has no `schedule`. Schedule ownership uses immutable `ProjectId`, never a Project name.
- Canonical identity remains: Schedule owner = `ProjectId`; Published snapshot = `(ProjectId, versionNumber)`; business milestone = `(ProjectId, milestoneId)`. Do not introduce a `DraftId`, `ScheduleId`, `VersionId`, `ScheduleVersionId`, `MilestoneRowId`, or mutable current pointer.
- Existing Published snapshots are immutable. Working Draft is not Official Truth, and every Draft transition returns replacement values without mutating inputs.
- `selectCurrentPublishedSchedule()` remains Current-Published-only and ignores both valid and malformed Working Draft content. A Draft defect must not make healthy Published truth unavailable.
- Start Draft is idempotent. It returns the exact existing Draft without overwriting edits; otherwise it copies the maximum-number Current Published snapshot or creates an empty Draft.
- Existing Draft milestones may change only `applicability`, `plan`, or `actual`. Their `milestoneId` and `milestoneDefinitionId` remain unchanged.
- Add receives one caller-allocated `MilestoneId`, uses an existing canonical milestone definition, and defaults to `applicable`, `plan: null`, `actual: null`. Removing and later adding the same definition creates a new milestone identity.
- Duplicate `milestoneDefinitionId` values are valid when `milestoneId` values differ. Duplicate `milestoneId` and unresolved `milestoneDefinitionId` are blocking Draft integrity defects.
- Empty Draft is valid and publishable. Do not invent Plan/Actual requirements, date chronology, milestone completeness, Stage completeness, date clearing for `notApplicable`, or catalog active/review-state rules.
- Publish revalidates Published history and the Draft, computes `max(versionNumber) + 1` itself, uses v1 for empty history, accepts non-contiguous history, rejects overflow at `Number.MAX_SAFE_INTEGER`, injects `publishedAt`, and always writes `versionNote: null`.
- Publish never uses `publishedVersions.length + 1` and accepts no caller-supplied version number. A UI preview may use the same pure next-version calculation but is not command authority.
- Publish creates a distinct immutable Published snapshot, atomically appends it and clears the Draft, and leaves all input state unchanged on failure.
- Cancel discards the complete Draft, leaves Published history untouched, reports no-Draft explicitly, and remains allowed for malformed Draft recovery.
- Valid Draft edits persist immediately through canonical commands and one reducer replacement. There is no separate Save Draft state or button; transient date text is presentation-only.
- Project Master remains the Workspace landing resource. Team remains disabled and labeled `Migration pending`.
- Dashboard Current Stage and MDRR remain `"-"`; Needs Attention remains `No items requiring attention.`; Milestone Due remains inactive; Export remains Task 2.1 all-Project behavior. Portfolio never reads Working Draft.
- Predecessor Schedule models, validators, commands, and workflow interpretations remain physically present but disconnected. Canonical code must not import predecessor Draft/Version/row identity or predecessor write APIs.
- Do not add Import, Evidence, Candidate, Proposal, Review, Rollback, Published-history UX, version comparison, Draft metadata, Team migration, Provider, Context store, repository, service, backend, database, login, or router architecture.
- Every behavior follows compiling behavioral RED, minimal GREEN, focused and adjacent verification, full suite, build, whitespace/static/scope audits, independent external review, then checkpoint commit. An unresolved import, module, or type cascade is not acceptable RED evidence.
- Every slice commit contains only its reviewed slice. Do not stage before external review. Do not amend or push. Stop at each slice boundary unless the human-approved execution request explicitly authorizes the next slice.
- Every slice reviewer classifies findings as Critical, Important, or Minor and provides the exact file/symbol/test, defect or risk, violated invariant, and correction. Critical and Important findings block commit; safe Minor corrections are applied, while any deferred Minor requires a concrete rationale.

```ts
export function validateScheduleWorkingDraft(
  draft: CanonicalScheduleWorkingDraft,
  definitions: readonly MilestoneDefinition[],
): readonly ValidationIssue[] {
  const definitionIds = new Set(definitions.map(({ id }) => id));
  const milestoneIds = new Set<MilestoneId>();
  const issues: ValidationIssue[] = [];

  for (const milestone of draft.milestones) {
    if (milestoneIds.has(milestone.milestoneId)) {
      issues.push(draftIssue(
        "schedule.draft.integrity.duplicate-milestone-id",
        "Working Draft milestone ID must be unique within the Draft.",
        milestone.milestoneId,
        "milestoneId",
      ));
    } else {
      milestoneIds.add(milestone.milestoneId);
    }
    if (!definitionIds.has(milestone.milestoneDefinitionId)) {
      issues.push(draftIssue(
        "schedule.draft.integrity.unresolved-milestone-definition",
        "Working Draft milestone must reference an existing milestone definition.",
        milestone.milestoneId,
        "milestoneDefinitionId",
      ));
    }
  }
  return issues;
}

export function orderScheduleWorkingDraftMilestonesByDefinition(
  milestones: readonly CanonicalScheduleWorkingDraftMilestone[],
  definitions: readonly MilestoneDefinition[],
): readonly CanonicalScheduleWorkingDraftMilestone[] {
  const order = new Map(definitions.map(({ id, displayOrder }) => [id, displayOrder]));
  return milestones
    .map((milestone, snapshotIndex) => ({ milestone, snapshotIndex }))
    .sort((left, right) =>
      (order.get(left.milestone.milestoneDefinitionId) ?? Number.POSITIVE_INFINITY) -
        (order.get(right.milestone.milestoneDefinitionId) ?? Number.POSITIVE_INFINITY) ||
      left.snapshotIndex - right.snapshotIndex)
    .map(({ milestone }) => milestone);
}
```

```tsx
function DateOnlyEditor({
  field,
  label,
  milestoneId,
  onValidValue,
  projectId,
  value,
}: DateOnlyEditorProps): React.ReactElement {
  const [text, setText] = React.useState<string>(value ?? "");

  React.useEffect(() => {
    setText(value ?? "");
  }, [field, milestoneId, projectId, value]);

  const acceptText = (nextText: string): void => {
    setText(nextText);
    if (nextText === "") {
      onValidValue(null);
      return;
    }
    const parsed = parseDateOnly(nextText);
    if (parsed !== null) onValidValue(parsed);
  };

  return (
    <input
      aria-label={label}
      onChange={(event) => acceptText(event.target.value)}
      type="text"
      value={text}
    />
  );
}
```
