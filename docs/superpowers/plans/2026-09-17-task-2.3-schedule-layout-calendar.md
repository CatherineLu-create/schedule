> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Retain the accepted Schedule below Resources layout and let users stage Draft Plan/Actual dates in the native control, then commit them only with explicit Apply Date or Clear.

**Architecture:** Layout Slice 1 is complete and human visually accepted at `cb37f9ba823c4c7ee942a03f255db3f55f3b6bd9`. Calendar Slice 2 keeps `App`'s mounted `PrototypeState` reducer and existing Schedule command bridge. `DateOnlyEditor` holds a temporary field candidate from its enabled native date input; native events never call the canonical callback. Apply Date submits a valid non-null candidate once, field Cancel abandons it, and explicit Clear submits null. No second Schedule authority or data model is introduced.

**Tech Stack:** React, TypeScript, Vite, Vitest, Testing Library, and native HTML `<input type="date">` with its built-in calendar indicator.

**Spec:** `docs/superpowers/specs/2026-09-18-task-2.3-calendar-apply-icon-design.md` supersedes immediate native-selection saving and the extra Calendar text trigger in `docs/superpowers/specs/2026-09-17-task-2.3-schedule-layout-calendar-design.md`. Read the older design and its referenced corrections/lifecycle designs only for preserved contracts.

## Global Constraints

- Project Workspace order is Project Master, Resources, one directly rendered Schedule Workspace, then existing feedback/content. The Schedule resource says `Shown below` and has no `Open Schedule` action.
- Draft Plan and Actual use small, enabled, mutable native date controls with visible native icons and Project/occurrence/field labels. Remove the extra Calendar text button and `showPicker()` handler. Keep native pointer and keyboard operation; if the target Windows browser lacks a usable mouse-operated native picker, stop for a human product decision.
- Native `input`, `change`, focus, blur, month/year navigation, and popup dismissal update no canonical state. A complete `YYYY-MM-DD` candidate passes unchanged through `parseDateOnly()` and the existing `onUpdateMilestone` callback as `DateOnly` only after one explicit Apply Date click. Explicit Clear alone sends `null`; field Cancel sends nothing. Do not use `Date`, `valueAsDate`, `valueAsNumber`, timezone conversion, or a slash-text adapter.
- Keep only temporary field candidates keyed to ProjectId, MilestoneId, and field. Display compact Apply Date/Cancel actions only for an active or unapplied field; keep `Remove` usable on the accepted desktop viewport and via the existing responsive table scroll. Preserve visible and accessible `Date not applied` feedback and the existing Publish guard, including an open confirmation, until Cancel or matching canonical props resolve each pending candidate. No new Publish business-completeness rule.
- Keep `PrototypeState.schedules` the sole embedded zero-or-one Draft authority by exact ProjectId. Accepted Draft edits survive Dashboard/Project navigation within the mounted app; Current Schedule and Portfolio remain Current Published-only. Preserve immutable max+1 Publish, Discard, malformed Draft recovery, confirmation reset, legal no-Published state, Dashboard `N/A`, A/A2, and catalog authority.
- Team Member, Weekly Report, and AVL remain disabled with `Migration pending`. No dependency, custom calendar, Save Draft, storage, backend, parser, fixture, timeout, or test-configuration work. Historical specs and corrective A-D plan stay unchanged. Task 2.3 remains open pending human UI acceptance.
