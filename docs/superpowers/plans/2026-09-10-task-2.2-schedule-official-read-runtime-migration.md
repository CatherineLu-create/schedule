# Task 2.2 — Schedule Official Read Runtime Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:executing-plans to implement this plan slice-by-slice.
> Each slice stops for independent external review before any checkpoint commit.

**Goal:** Establish `PrototypeState.schedules` as the sole canonical Schedule authority, derive Current Published by maximum version number, initialize an empty Schedule atomically with each new Project, and enable a read-only canonical Schedule Workspace without migrating Schedule writes, Team, or Portfolio behavior.

**Architecture:** Five sequential slices introduce the official-read domain model, explicit canonical fixtures, an atomic removal of embedded `Project.schedule` while adding root Schedule ownership, a discriminated application read boundary, and the read-only Workspace. `PrototypeState.projects` remains Project/Master authority; `PrototypeState.schedules` owns one Schedule per immutable `ProjectId`; disconnected predecessor Schedule-write types may remain but cannot enter canonical Project state, canonical reducer actions, runtime fixtures, or official reads.

**Tech Stack:** TypeScript (strict, ES2022), React, ReactDOM, Vitest, React Testing Library, jsdom, Vite, Tailwind CSS, and SheetJS (`xlsx`).

**Spec:**
`docs/superpowers/specs/2026-09-10-task-2.2-schedule-official-read-runtime-migration-design.md`

## Global Constraints

- `PrototypeState.projects` remains the sole writable Project/Master collection.
- `PrototypeState.schedules` becomes the sole canonical Schedule collection. No canonical Project, Project command result, reducer payload, fixture, selector input, or Workspace read may carry embedded Schedule business state after Slice 3.
- Each canonical Project owns exactly one canonical Schedule through the same immutable `ProjectId`. Schedule has no `ScheduleId`; Project names are never ownership keys.
- A valid no-Published state is one Schedule with `publishedVersions: []`. A missing Schedule is an integrity failure and must never be converted to the valid empty state during read.
- A Published version is identified by `(ProjectId, versionNumber)`. `versionNumber` is a positive safe integer and unique inside one Schedule. No `ScheduleVersionId`, `VersionId`, or mutable current pointer belongs to the official-read model.
- Current Published is derived in one domain function as the maximum `versionNumber`, independent of array order. Non-contiguous positive version numbers are valid.
- Published versions and milestones are readonly snapshots. Task 2.2 adds no reducer action, command, editor, or callback that mutates or replaces Published data.
- `milestoneId` is immutable business-lineage identity and is unique within one Published version. Reusing the same `milestoneId` across versions of the same Project is valid. `milestoneDefinitionId` is classification, and milestone names are not identity.
- The canonical Published milestone contains only `milestoneId`, `milestoneDefinitionId`, `applicability`, `plan`, and `actual`. It contains no Draft, row, import, evidence, proposal, review, publish-command, rollback, or document metadata.
- Resolvable milestones display by existing catalog `displayOrder`; equal order preserves Published snapshot array order. No date, name, status, or ID sorting is introduced.
- Phase has no canonical source and displays `"-"`. Stage and Milestone labels come from the existing V2 `stageGroupCatalog` and `milestoneDefinitions`. Null dates display `"-"`; unresolved milestone definitions make the Schedule unavailable.
- Explicit `canonicalScheduleFixtures` initialize runtime Schedule state. There is no live legacy-to-canonical adapter and no fabricated Published history for all five Projects.
- Project creation remains the Task 2.1 command/interpreter flow. Only a completed Create dispatches one atomic `projectAdded` action containing the returned Project and one empty Schedule with the same `ProjectId`. Rejected and duplicate-review outcomes do not dispatch. Create Anyway retains the original ID.
- Workspace still lands on Project Master. Schedule becomes enabled and shows only Current Published read-only. Team remains disabled and labeled `Migration pending`.
- `noPublishedSchedule`, `published` with zero milestones, and `unavailable` are distinct result and UI states. An absent selected Project ID is also `unavailable`; Task 2.1 selection cleanup still prevents stale Workspace rendering.
- `selectOfficialProjectSources()` must no longer expose the lossy embedded `latestPublishedSchedule` member. The canonical Schedule read boundary owns Schedule lookup, integrity, Current Published selection, and presentation ordering.
- Dashboard Current Stage and MDRR remain `"-"`; Needs Attention remains `No items requiring attention.`; Dashboard and Export retain Task 2.1 behavior. Working Draft never enters official reads.
- Legacy Schedule files may remain physically present, but `src/main.tsx`, canonical state, fixtures, reducers, and official selectors must not import or invoke legacy Schedule JSON, state, filters, version history, write actions, or live adapters.
- Existing predecessor Schedule write functions may be mechanically decoupled from canonical `Project` only as required for compilation and regression preservation. Their behavior must not be extended, and they must remain unreachable from canonical state/runtime.
- No Provider, Context/store framework, repository, service, adapter framework, persistence, backend, router, or new application architecture is introduced.
- No Working Draft, Create Draft, Edit Schedule, Import, Evidence, Candidate, Proposal, Review, Publish, rollback, history selector, Portfolio Schedule derivation, Team migration, Milestone Due, or warning activation is implemented.
- Every behavioral slice follows RED → GREEN. RED must demonstrate missing approved behavior, not a bad import, malformed test fixture, or unrelated TypeScript failure.
- Do not modify the approved design spec. Do not begin Task 2.3. Do not push.

```ts
import type { MilestoneDefinition } from "./milestoneCatalog";
import type { MilestoneApplicability, ScheduleVersionNumber } from "./schedule";
import type { DateOnly } from "../shared/dateOnly";
import type {
  MilestoneDefinitionId,
  MilestoneId,
  ProjectId,
} from "../shared/ids";
import type { ValidationIssue } from "../validation/validationIssue";

export interface CanonicalPublishedScheduleMilestone {
  readonly milestoneId: MilestoneId;
  readonly milestoneDefinitionId: MilestoneDefinitionId;
  readonly applicability: MilestoneApplicability;
  readonly plan: DateOnly | null;
  readonly actual: DateOnly | null;
}

export interface CanonicalPublishedScheduleVersion {
  readonly versionNumber: ScheduleVersionNumber;
  readonly versionNote: string | null;
  readonly publishedAt: string;
  readonly milestones: readonly CanonicalPublishedScheduleMilestone[];
}

export interface CanonicalProjectSchedule {
  readonly projectId: ProjectId;
  readonly publishedVersions: readonly CanonicalPublishedScheduleVersion[];
}

export function createEmptyCanonicalProjectSchedule(
  projectId: ProjectId,
): CanonicalProjectSchedule;

export function getCurrentPublishedVersion(
  schedule: CanonicalProjectSchedule,
): CanonicalPublishedScheduleVersion | null;

export function orderPublishedMilestonesByDefinition(
  milestones: readonly CanonicalPublishedScheduleMilestone[],
  definitions: readonly MilestoneDefinition[],
): readonly CanonicalPublishedScheduleMilestone[];

export function validateCanonicalProjectSchedule(
  schedule: CanonicalProjectSchedule,
  definitions: readonly MilestoneDefinition[],
): readonly ValidationIssue[];
```

Add `MilestoneId` and `toMilestoneId(value: string)` to `src/domain/shared/ids.ts`. Retain predecessor `ScheduleVersionId`, `ScheduleDraftId`, and `MilestoneRowId` only for disconnected predecessor types/tests; never use them in `CanonicalProjectSchedule`.

`validateCanonicalProjectSchedule()` emits blocking, data-source Schedule issues using these exact codes:

- `schedule.integrity.invalid-version-number`
- `schedule.integrity.duplicate-version-number`
- `schedule.integrity.duplicate-milestone-id`
- `schedule.integrity.unresolved-milestone-definition`

It validates only approved read integrity. It must not validate date chronology, applicability completeness, publication timestamp format, definition active/review status, version contiguity, or due/completeness policy.

Ownership issues use these exact blocking/data codes:

- `schedule.integrity.project-not-found`
- `schedule.integrity.missing-schedule`
- `schedule.integrity.duplicate-schedule`
- `schedule.integrity.orphan-schedule`

`selectCurrentPublishedSchedule()` never chooses from duplicate entries, creates a missing entry, drops a malformed version, or falls back to legacy data. A `published` result is emitted only after the selected Schedule passes local validation. The Workspace-facing result exposes only the selected Current Published snapshot, not the owning Schedule or historical versions. Whole-state validation remains separately reportable; an unrelated orphan or malformed Schedule does not suppress an otherwise valid selected Project's Schedule. `versionLabel` is presentation-only: `Published v${String(versionNumber).padStart(2, "0")}`.
